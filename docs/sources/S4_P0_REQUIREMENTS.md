# 1. 文档定位与需求概述

## 1.1 文档定位

本文件用于统一说明“大光路智慧社区 P0 商城闭环”整体要建设什么、业务如何闭环、包含哪些需求和菜单、所有阶段共同遵守哪些规则，以及为什么拆分为当前六个阶段。

本文件不替代阶段产品需求详细设计，也不展开数据库、Controller、Service、DTO、代码结构或详细 API 技术协议。

后续文档关系如下：

```text
P0 商城闭环总体需求大纲
        ↓
P0 商城闭环产品开发总清单与六阶段计划
        ↓
00A / 01～05 各阶段产品需求详细设计
        ↓
住户小程序 / 商户小程序前端原型
        ↓
研发实施
        ↓
测试与产品验收
```

原则：

- 总体需求大纲负责冻结整体产品边界与跨阶段规则；
- 开发总清单负责明确功能范围、复用方式和阶段归属；
- 阶段详细设计负责把具体菜单设计到研发和测试可直接实施的深度；
- 前端原型负责页面布局、信息层级和交互表现；
- 下游文档不得擅自改变总体大纲已冻结的核心业务决策。

## 1.2 需求背景

大光路智慧社区需要形成面向社区居民、本地商户和平台运营人员的社区商城能力。

平台需要解决三类核心问题：

1. **商户供给侧**：商户能够申请入驻、完成审核和合作关系建立，并持续维护商品、库存和履约能力；
2. **居民交易侧**：居民能够在智慧社区住户小程序中浏览、购买、支付、收货、自提、核销、售后和评价；
3. **平台运营与资金侧**：平台能够审核商户和商品、监管订单及售后，并基于微信支付平台收付通完成支付、分账、退款、必要分账回退和资金核对。

P0 商城以 LiLiShop 为唯一商城业务底座，优先复用其 Goods、GoodsSku、Cart、Trade、Order、Payment、AfterSale、Evaluation、StoreFlow 等成熟能力，不重新建设第二套商城内核。

## 1.3 建设目标

最终形成如下完整业务闭环：

```text
商户申请入驻
→ 平台审核
→ 合作协议及经营资格
→ 商品创建
→ 商品审核
→ 商品上架
→ 居民浏览商品
→ 加购物车 / 立即购买
→ 多商户统一结算
→ 微信支付平台收付通
→ 商户按订单履约
→ 居民确认 / 自提 / 到店核销
→ 订单完成
→ 售后退款 / 退货
→ 商品评价
→ 平台分账
→ 已分账订单退款时必要分账回退
→ 商户查看资金结果
→ 平台异常处理与基础对账
```

P0 完成后，应满足：

- 居民可以完成真实商城交易；
- 商户可以完成完整经营和履约；
- 平台可以完成准入、审核、监管和资金闭环；
- 三端使用同一真实后端业务事实；
- 资金结果能够从订单追溯到支付、退款、分账和回退。

# 2. 产品端、角色与核心业务对象

## 2.1 产品端

| 产品端 | 主要使用角色 | P0 主要职责 |
|---|---|---|
| 管理后台 Web | 平台运营、审核、财务、系统管理员 | 商户准入、协议与资格、商品监管、订单监管、售后监管、平台收付通及资金管理 |
| 住户小程序 | 社区居民 | 商品浏览、购物车、下单、支付、收货、自提/核销、售后、评价 |
| 商户小程序 | 商户负责人、商户工作人员 | 入驻资料、商品经营、订单履约、核销、售后处理、资金结果查看 |

住户小程序仍是智慧社区统一入口，商城是其中一个业务域，不将住户小程序重构为独立商城 App。

## 2.2 主要角色

| 角色 | 主要职责 | 主要端 |
|---|---|---|
| 居民 | 浏览商品、下单支付、收货/核销、售后、评价 | 住户小程序 |
| 商户负责人 | 入驻、资料、商品、工作人员、订单、售后、资金查看 | 商户小程序 |
| 商户工作人员 | 按授权处理商品、订单、核销、售后 | 商户小程序 |
| 平台运营/审核 | 商户审核、商品审核、订单与售后监管 | Web |
| 平台财务/管理员 | 平台收付通、分账、退款、资金异常与对账 | Web |

## 2.3 核心业务对象

| 对象 | 产品定义 | 主要关系 |
|---|---|---|
| Store | 商户在商城中的经营店铺 | 关联商户资料、商品、订单、二级商户、协议和资金规则 |
| Goods | 商品 SPU 主体 | 属于 Store，下含一个或多个 SKU |
| GoodsSku | 商品实际可交易规格 | 承载价格、库存、规格等交易事实 |
| Cart | 居民购物车条目 | 按 Store 聚合参与结算 |
| Trade | 一次居民统一结算与合单支付容器 | 可包含多个 Store Order |
| Store Order | 一个 Store 的实际业务订单 | 一个商户、一种履约方式、多个 OrderItem |
| OrderItem | Store Order 中具体商品/SKU | 售后、评价和金额分摊的基础粒度 |
| Payment | Trade 的支付事实 | 关联微信平台收付通渠道结果 |
| Fulfillment | Store Order 的履约事实 | 商户配送、普通物流、社区自提、到店核销之一 |
| AfterSale | 售后业务对象 | 关联 Store Order / OrderItem，支持退款和退货 |
| Evaluation | 订单项评价 | 订单完成后的商品评价 |
| ProfitSharing | 分账业务事实 | 关联支付、Store Order、佣金规则和渠道结果 |
| ProfitSharingReturn | 分账回退事实 | 已分账订单发生退款时关联原分账 |
| StoreFlow | 商户流水摘要 | 用于业务资金摘要，不替代渠道最终结果 |

## 2.4 核心对象关系

```text
Member
 └─ Cart
     └─ Trade
         ├─ Store Order A
         │   ├─ OrderItem
         │   ├─ Fulfillment
         │   ├─ AfterSale
         │   └─ ProfitSharing / ProfitSharingReturn
         │
         └─ Store Order B
             ├─ OrderItem
             ├─ Fulfillment
             ├─ AfterSale
             └─ ProfitSharing / ProfitSharingReturn

Store
 ├─ StoreDetail / 资质
 ├─ 合作协议
 ├─ 经营资格
 ├─ 平台收付通二级商户
 ├─ Goods / GoodsSku
 └─ 履约点位
```

# 3. 总体业务流程

## 3.1 商户供给链

```text
商户登录 / 申请身份
→ 填写入驻资料
→ 平台审核
→ 形成 Store
→ 建立合作协议
→ 维护必要资质
→ 形成经营基础资格
→ 完成平台收付通二级商户条件
→ 形成正式交易资格
→ 创建商品 / SKU
→ 提交商品审核
→ 平台审核
→ 商品上架
```

关键结果：

- “审核通过”不等于“正式交易资格 READY”；
- 商户能否上架和交易由多项真实业务条件共同决定；
- 商品历史和订单历史不能因为后续资格变化被删除。

## 3.2 居民交易链

```text
首页商城入口
→ 商城首页 / 搜索 / 分类
→ 商品详情
→ 加购物车 / 立即购买
→ 按 Store 聚合已选商品
→ 校验每个 Store 的共同可用履约方式
→ 一个 Trade
→ 多个 Store Order
→ 平台收付通合单支付
→ 支付成功
→ 各 Store Order 独立进入履约
```

## 3.3 订单拆分与履约链

P0 订单拆分规则：

```text
一次结算
→ 按 Store 拆 Store Order
→ 每个 Store Order 只能选择一种履约方式
```

四种履约方式：

```text
商户配送
社区自提
到店核销
普通物流
```

不同 Store Order 可以选择不同履约方式，但一个 Store Order 内不支持混合履约。

### 商户配送

```text
已支付
→ 待备货
→ 待配送
→ 配送中
→ 已送达
→ 居民确认
→ 已完成
```

### 普通物流

```text
已支付
→ 待备货
→ 待发货
→ 已发货
→ 居民确认
→ 已完成
```

### 社区自提

```text
已支付
→ 待备货
→ 待自提
→ 商户核销
→ 已完成
```

### 到店核销

```text
已支付 / 已就绪
→ 待核销
→ 商户核销
→ 已完成
```

## 3.4 售后链

P0 售后只支持：

```text
退款
退货
```

总体链路：

```text
居民发起售后
→ 系统校验可售后数量和可退金额
→ 商户审核
   ├─ 拒绝 → 售后结束
   ├─ 同意退款 → 等待资金退款
   └─ 同意退货 → 居民退货 → 商户确认收货 → 等待资金退款
→ 统一资金处理
→ 渠道退款成功
→ 售后完成
```

售后原则上以 OrderItem 为申请粒度，支持部分数量和部分金额，但不能重复占用同一退款额度。

## 3.5 评价链

```text
订单完成
→ 满足评价条件
→ 居民提交星级 / 文字 / 图片
→ 形成评价
→ 商户只读查看
→ 平台按 LiLiShop 原能力监管
→ 商品公开评价数据更新
```

## 3.6 资金链

P0 统一使用：

**微信支付平台收付通**

总体资金链：

```text
Trade 合单支付
→ 多个 Store Order 对应不同二级商户
→ 支付完成
→ 订单履约完成
→ 根据订单资金规则快照计算分账
→ 发起分账
→ 查询最终结果
```

发生售后时：

### 尚未分账

```text
售后达到退款条件
→ 阻止对应金额进入后续分账
→ 发起退款
→ 查询最终结果
→ 售后完成
```

### 已经分账

```text
售后达到退款条件
→ 查询原实际分账结果
→ 计算必要分账回退
→ 分账回退
→ 回退成功
→ 发起退款
→ 查询退款结果
→ 售后完成
```

### 分账状态未知 / 处理中

```text
先查询最终分账事实
→ 再决定退款路径
```

# 4. 全局业务规则与产品决策

以下规则为 P0 商城所有阶段共同遵守的最高产品规则。

| 编号 | 规则 |
|---|---|
| BR-01 | 商城唯一业务后端底座为 LiLiShop，不重新建设第二套 Goods、SKU、Cart、Trade、Order、Payment、AfterSale、Evaluation 内核。 |
| BR-02 | P0 仅服务大光路单一社区，不建设 Project 管理和多社区切换。 |
| BR-03 | 住户小程序保持智慧社区统一门户，商城是其中一个业务入口。 |
| BR-04 | 商户使用独立商户小程序；管理后台以 LiLiShop Manager 为基础。 |
| BR-05 | 一次居民结算形成一个 Trade，Trade 可以包含多个 Store Order。 |
| BR-06 | Store Order 按 Store 拆分，一个 Store Order 仅属于一个商户。 |
| BR-07 | 一个 Store Order 只允许一种履约方式，不支持单订单混合履约。 |
| BR-08 | 同一 Store 下多个已选商品必须存在共同可用履约方式；无交集时阻止结算并提示分开结算。 |
| BR-09 | 不因同一 Store 商品履约冲突自动拆成多个 Store Order，P0 由居民自行分开结算。 |
| BR-10 | 商城支付统一采用微信支付平台收付通。 |
| BR-11 | 商户在平台收付通资金体系中的核心身份为二级商户，不按“平台收全款后再将大部分货款分给普通分账接收方”的旧模型设计。 |
| BR-12 | 平台收付通正式账户和二级商户条件未就绪前，允许使用与正式模型一致的 Mock 通道完成业务研发和阶段验收。 |
| BR-13 | Mock 支付必须模拟 Trade、多 Store Order、支付状态、回调、主动查询、取消、关闭等真实业务结构，不使用仅有“模拟成功”的假流程。 |
| BR-14 | 阶段2可在 Mock 支付业务验收通过后退出；真实平台收付通渠道验收可后置，但 P0 最终验收必须完成真实支付、分账、退款及必要分账回退。 |
| BR-15 | 商品、价格、地址、履约点位、买家留言、资金规则等已发生订单必须使用历史快照，后续主数据变化不得覆盖历史事实。 |
| BR-16 | Order 主状态、履约状态、售后状态、退款状态、分账状态、回退状态均为独立业务事实，不使用单一状态字段替代整个业务链。 |
| BR-17 | StoreFlow 只作为商户资金业务摘要，不替代微信渠道实际支付、退款、分账和回退结果。 |
| BR-18 | 商户只能访问本人 Store 的商品、订单、售后和资金；前端传参不能扩大数据范围。 |
| BR-19 | 居民只能访问本人购物车、地址、订单和售后。 |
| BR-20 | 商户停业、协议到期或资格失效后，禁止新增经营行为，但历史已支付订单仍允许必要履约、售后、退款和资金处理。 |
| BR-21 | 前端按钮和页面控制仅用于改善体验，后端必须在每个关键操作重新校验身份、数据归属、状态和业务前置条件。 |
| BR-22 | 金额展示使用元，交易和资金核算使用分；关键金额不得依赖前端浮点计算。 |
| BR-23 | 外部渠道“已受理”不等于最终成功；支付、退款、分账和回退状态未知时必须查询真实结果。 |
| BR-24 | 关键写操作必须考虑重复提交和并发，不能因重试生成重复订单、重复核销、重复退款、重复分账或重复回退。 |
| BR-25 | 居民端不得展示平台佣金、商户应得、分账比例和回退内部资金信息。 |

# 5. P0 需求清单

需求清单按“要解决什么业务问题”拆分，不按页面拆分。

## 5.1 商户准入与经营资格

| 需求编号 | 需求 |
|---|---|
| D01 | 商户负责人可以在商户小程序发起入驻申请，并保存草稿、提交和驳回后重提。 |
| D02 | 平台可以在 Web 审核商户申请，并保留审核结果和历史记录。 |
| D03 | 审核通过后形成正式 Store，并允许维护商户、店铺和必要资质。 |
| D04 | 平台可以与商户建立轻量合作协议，并维护协议有效期和状态。 |
| D05 | 系统可以根据商户、资质、协议等事实计算经营基础资格。 |
| D06 | 系统可以根据经营基础资格、平台收付通二级商户条件和资金规则计算正式交易资格。 |
| D07 | 商户和平台均可以查看经营资格结果及不满足原因。 |

## 5.2 商品供给

| 需求编号 | 需求 |
|---|---|
| D08 | 商户可以维护商品、SKU、价格、库存、图片、详情和履约方式。 |
| D09 | 商品可以保存草稿、提交审核、驳回修改并重新提交。 |
| D10 | 平台可以审核商品，并对已上架商品进行监管和强制下架。 |
| D11 | 商品提交审核和上架时必须重新校验商户经营资格。 |
| D12 | 商户可以维护社区自提和到店核销所需履约点位。 |

## 5.3 居民商品发现与购物车

| 需求编号 | 需求 |
|---|---|
| D13 | 居民可以从智慧社区首页进入商城。 |
| D14 | 居民可以通过分类、关键词和排序查找可售商品。 |
| D15 | 居民可以查看商品详情、SKU、库存、店铺及履约提示。 |
| D16 | 居民可以将商品加入购物车并修改数量、删除和清理失效商品。 |
| D17 | 购物车按 Store 分组，并支持多个 Store 商品一次统一结算。 |

## 5.4 结算与支付

| 需求编号 | 需求 |
|---|---|
| D18 | 一次统一结算生成一个 Trade，并按 Store 拆分多个 Store Order。 |
| D19 | 每个 Store Order 只能选择一种履约方式。 |
| D20 | 同一 Store 多商品结算前必须计算共同可用履约方式。 |
| D21 | 居民可以维护收货地址，并区分默认地址和本次结算选择地址。 |
| D22 | 订单创建时固化商品、价格、地址、点位、留言和资金规则快照。 |
| D23 | 交易提交必须幂等，并正确处理库存和失败补偿。 |
| D24 | 多 Store Order 可以通过平台收付通进行一次合单支付。 |
| D25 | 支付支持待支付、处理中、成功、失败、关闭和主动查询。 |
| D26 | 正式渠道未就绪时可用 Mock 平台收付通完成业务验收。 |

## 5.5 订单与履约

| 需求编号 | 需求 |
|---|---|
| D27 | 住户、商户和 Web 能基于同一 Store Order 查看符合权限的数据。 |
| D28 | 商户可以对商户配送订单完成备货、开始配送和确认送达。 |
| D29 | 商户可以对普通物流订单完成备货、填写物流公司/单号并发货。 |
| D30 | 居民可以查看配送/物流进度并确认收货。 |
| D31 | 社区自提订单完成备货后，居民可以出示凭证，商户核验后完成订单。 |
| D32 | 到店核销订单可由居民出示凭证，商户核验后完成订单。 |
| D33 | 扫码或输码仅查询订单，必须人工确认后才真正核销。 |
| D34 | 履约操作不得重复扣减库存。 |
| D35 | Web 能监管订单和核销记录，但不得无规则直接修改业务状态。 |

## 5.6 售后与评价

| 需求编号 | 需求 |
|---|---|
| D36 | 居民可以按 OrderItem 申请退款或退货。 |
| D37 | 售后支持部分数量和部分退款额度，并防止重复占用。 |
| D38 | 商户可以同意、拒绝售后，并在拒绝时填写原因。 |
| D39 | 退货售后支持居民填写退货物流和商户确认收货。 |
| D40 | 商户同意售后不等于渠道退款成功，售后需等待统一资金处理。 |
| D41 | 活动售后可以按规则阻断相关未完成履约。 |
| D42 | 已完成订单满足条件后，居民可以提交商品评价。 |
| D43 | 商户和平台可以查看符合权限的评价。 |

## 5.7 资金闭环

| 需求编号 | 需求 |
|---|---|
| D44 | 平台采用微信支付平台收付通，商户作为二级商户管理。 |
| D45 | 平台可以管理平台收付通二级商户进件和渠道状态。 |
| D46 | 平台可以按商户合作规则维护平台佣金规则，并在订单创建时固化资金快照。 |
| D47 | 订单完成后，满足条件的 Store Order 可以生成唯一分账任务。 |
| D48 | 平台可以查询每笔分账的实际渠道结果。 |
| D49 | 尚未分账的售后退款金额不得继续进入后续分账。 |
| D50 | 已分账订单退款时，系统可以根据原实际分账结果计算和执行必要分账回退。 |
| D51 | 分账状态未知或处理中时，退款必须先查询最终资金事实。 |
| D52 | 平台可以处理支付、退款、分账和回退异常，并进行合法查询和重试。 |
| D53 | 平台可以按订单关联支付、退款、分账和回退，完成基础资金核对。 |
| D54 | 商户可以查看本人 Store 的订单资金结果和最终净额。 |
| D55 | 居民仅查看退款结果，不查看平台分账和佣金内部信息。 |

# 8. 跨阶段通用准则

## 8.1 复用准则

- LiLiShop 已具备的成熟商城对象优先直接复用；
- 大光路差异通过字段、规则、状态或页面适配解决；
- 只有 LiLiShop 缺失且属于 P0 必需的业务对象才重新开发；
- 不因前端采用自研小程序就重建商城后端。

## 8.2 数据与历史准则

- 主数据与历史交易事实分离；
- 已发生订单保存关键快照；
- 主数据后续编辑不覆盖历史订单；
- 商户关闭、协议失效、点位停用不删除历史业务；
- 关键状态变化保留操作记录和时间。

## 8.3 交易一致性准则

- 前端校验不能代替后端校验；
- 关键写操作必须幂等；
- 并发情况下只能产生一个有效业务结果；
- 未知结果先查询真实事实，再决定是否重试；
- 不通过删除失败记录来“恢复”交易。

## 8.4 权限与数据隔离准则

- 居民只访问本人数据；
- 商户按当前 Store 隔离；
- Web 按角色和菜单/按钮权限管理；
- 前端参数不得扩大数据范围；
- 商户历史订单处理权与新增经营资格分开判断。

## 8.5 金额准则

- 页面金额展示使用元；
- 后端及渠道金额使用分；
- 订单、退款、分账、回退金额均可追溯；
- 不使用前端浮点计算作为最终交易金额；
- 分账和退款使用历史资金快照，不使用当前新规则覆盖旧订单。

## 8.6 外部渠道准则

- 平台收付通正式账户未就绪不阻塞前期业务研发；
- Mock 与正式渠道使用一致业务抽象；
- 渠道受理不等于成功；
- 支付、退款、分账、回退均需要最终结果确认；
- 正式资金功能上线前必须补真实渠道验证。

# 9. 六阶段总体计划

| 阶段 | 阶段目标 | 核心前置 | 主要结果 |
|---|---|---|---|
| 阶段0 研发前置 | 双小程序用户身份可用 | AppID及微信基础条件 | 住户和商户可以稳定登录并形成正确业务身份 |
| 阶段1 商户准入与商品供给 | 商户和商品可以真实进入交易准备状态 | 阶段0 | Store、协议、资格、二级商户前置、Goods/SKU/点位可用 |
| 阶段2 住户商城交易与支付 | 可以完成多商户统一结算和支付业务闭环 | 阶段1 | Trade、多 Store Order、单订单单履约、Mock/正式支付业务链路 |
| 阶段3 三端订单与商城履约 | 四种履约方式全部走通 | 已支付订单 | Web/住户/商户三端订单一致并产生完成订单 |
| 阶段4 商城售后与评价 | 售后业务和评价走通 | 阶段3订单 | 退款/退货进入待资金处理，评价可用 |
| 阶段5 资金分账与退款闭环 | 正式资金闭环收口 | 支付、完成订单、售后 | 真实支付、分账、退款、必要回退、异常和对账完成 |

## 9.1 阶段依赖

```text
阶段0 身份
  ↓
阶段1 Store / Goods / SKU
  ↓
阶段2 Trade / Payment
  ↓
阶段3 Fulfillment / Completed Order
  ↓
阶段4 AfterSale / Evaluation
  ↓
阶段5 ProfitSharing / Refund / Return / Reconciliation
```

平台收付通正式账户申请可与阶段0～4业务研发并行，不作为这些阶段代码研发的硬阻塞项；但阶段5及 P0 最终验收必须使用真实渠道完成验证。

# 10. 阶段退出标准

## 10.1 阶段0

- 住户真实微信登录成功；
- 同一微信用户稳定关联同一个 Member；
- 商户负责人、工作人员和未入驻申请身份规则明确；
- 双小程序 AppID、会话、身份隔离；
- 微信开发者工具/真机最小验证通过。

## 10.2 阶段1

- 商户可完整申请、审核、驳回重提；
- Store、店铺资料、资质、协议可用；
- 基础经营资格和正式交易资格可解释；
- 平台收付通二级商户前置状态可管理；
- 商品/SKU/库存可维护、审核、上架；
- 履约点位可供结算使用；
- 至少存在可被住户真实调用的可售商品。

## 10.3 阶段2

- 商品发现、购物车、地址、确认订单链路完整；
- 一个 Trade 可拆多个 Store Order；
- Store Order 单一履约规则生效；
- 同 Store 无共同履约方式时阻止结算；
- 交易幂等和库存处理正确；
- 平台收付通 Mock 业务闭环通过；
- 真实渠道状态可以暂记 PENDING，但必须形成后续补验项。

## 10.4 阶段3

- 商户配送、普通物流、社区自提、到店核销全部走通；
- Web、住户、商户三端核心订单事实一致；
- Store 数据隔离正确；
- 核销查询与确认两步分离；
- 履约不重复扣库存；
- 产生真实已完成订单。

## 10.5 阶段4

- 退款申请、商户同意/拒绝流程通过；
- 退货申请、居民退货、商户确认收货流程通过；
- 售后额度、部分数量、并发控制正确；
- 售后和履约联动正确；
- 商品评价通过；
- 售后可以进入待资金处理。

## 10.6 阶段5

- 真实平台收付通支付验证通过；
- 正常订单真实分账通过；
- 未分账退款通过；
- 已分账订单分账回退后退款通过；
- 支付、分账、退款、回退异常查询和合法重试通过；
- 商户资金结果正确；
- Web 可追溯订单全部资金事实；
- 基础对账可识别关键差异。

## 11.1 商户侧

- 可以跨多个 Store 统一结算；
- 可以微信支付；
- 可以查看并确认履约结果；
- 可以自提和到店核销；

- 可以审核商户和商品；
- 可以监管订单和售后；
- 可以通过平台收付通完成真实支付；

- 可以完成退款；
- 可以完成必要分账回退；
- 可以查询异常和执行合法重试；

至少完成：

6. 到店核销；
7. 未分账退款；
8. 已分账订单退款与分账回退；
9. 退货退款；
10. 商品评价；
11. 商户资金结果查看；

# 12. 下游文档与变更治理

## 12.1 文档层级

```text
第1层：P0 商城闭环总体需求大纲
    ↓
第2层：产品开发总清单与六阶段计划
    ↓

    ↓
第4层：前端原型
    ↓
```

## 12.2 变更原则

以下内容如需变化，必须优先修改总体需求大纲：

- P0 范围；
- 产品端；
- Trade / Store Order 核心关系；
- 履约拆单规则；
- 支付模式；
- 售后类型；
- 分账及退款主路径；
- 阶段数量和阶段目标；
- P0 最终验收标准。

阶段详细设计可以补充字段、交互、状态、权限和异常，但不得与总体需求大纲冲突。

## 12.3 待确认事项管理

不确定但不阻塞主体设计的事项：

- 在对应阶段详细设计中标记“待确认”；
- 不得擅自扩展成 P0 新功能；
- 如最终影响全局业务规则，确认后回写本总体需求大纲。
