> 目标版本：V1.0 基础运营可用版  
> 计划时间：2026年8月—2026年11月  
> 一期截止：**2026年11月30日**  
> 业务终端：管理后台 Web、住户小程序、商户小程序  
> 一期业务优先级：**P1 商城闭环 → P2 社区服务闭环 → P3 物业缴费与房屋绑定 → P4 居民共享与邻里互助 → P5 停车缴费**  
> 配套能力：平台基础、商户准入、微信支付/退款/分账、最小积分、消息等按业务依赖穿插建设

# 1. 一期版本目标

V1.0不以功能菜单数量作为完成标准，而以五条业务闭环能够稳定运行作为一期完成标准；积分、消息、支付分账等作为支撑能力穿插建设。

## 1.1 商城运营闭环

```text
商户提交入驻
→ 平台Web审核
→ 建立合作协议与经营授权
→ 建立微信支付/分账关系
→ 商户发布商品
→ 平台审核上架
→ 居民浏览、加购、下单
→ 微信小程序支付（需分账订单设置分账标识）
→ 商户备货
→ 商户配送 / 社区自提 / 到店核销
→ 订单完成
→ 按订单分账规则快照计算分账金额
→ 微信分账
→ 查询最终分账结果 / 解冻剩余资金
→ 发放消费积分
→ 售后、退款、评价
```

## 1.2 社区服务闭环

```text
服务商户入驻/审核/协议
→ 发布服务
→ 平台审核
→ 居民选择服务、规格、时间、地址
→ 创建服务预约/订单
→ 收费服务微信支付
→ 商户/服务人员接单
→ 到场
→ 开始服务
→ 服务过程与时效记录
→ 完成
→ 微信分账
→ 发放积分
→ 评价 / 售后
```

## 1.3 积分闭环

```text
商城/服务有效消费
→ 按“积分获取规则”计算并发放积分
→ 居民积分账户/积分流水

居民缴纳物业费
→ 按“积分抵扣规则”计算可抵扣金额
→ 居民选择使用积分
→ 扣减/占用积分
→ 微信支付剩余金额
→ 缴费成功
```

## 1.4 房屋与物业费闭环

```text
居民微信登录
→ 申请/确认绑定房屋
→ 查询本人房屋物业费账单
→ 按规则使用积分抵扣（如启用）
→ 微信支付剩余金额
→ 支付回调更新账单
→ 生成缴费记录
```

## 1.5 居民共享与邻里互助闭环

```text
居民实名认证 + 社区身份校验
→ 发布闲置共享 / 互助需求 / 低风险技能服务
→ 平台审核
→ 社区范围内展示
→ 其他居民发起意向 / 认领 / 接单
→ 线下交付或互助服务完成
→ 双方确认
→ 评价 / 举报
```

一期定位为社区内轻撮合和互助闭环，不建设个人在线收款、平台资金托管、复杂二手交易售后和高风险个人服务。

## 1.6 停车缴费闭环

```text
居民微信登录
→ 维护/确认车辆信息
→ 建立车辆与居民/停车关系
→ 查询停车费账单
→ 微信支付
→ 支付回调更新账单
→ 生成停车缴费记录
```

一期只建设车辆、关系、停车费账单和缴费，不建设停车场设备、闸机、车牌识别、车位实时占用等设备平台能力。

# 2. 一期范围调整结论

## 2.1 一期必须建设

按业务优先级排序：

1. **P1 社区商城闭环**：商户入驻/合作关系、商品、订单、支付、履约、分账、退款；
2. **P2 社区服务闭环**：服务供给、预约、支付、接单、到场、开始、完成、分账/退款；
3. **P3 物业缴费与房屋绑定**：社区/楼栋/房屋、居民、人房关系、房屋绑定、物业费账单与缴费；
4. **P4 居民共享与邻里互助**：闲置共享、低风险技能/互助需求发布审核、社区展示、撮合/认领、完成确认、评价举报；
5. **P5 停车缴费**：车辆档案、车辆/居民/停车关系、停车费账单、微信缴费和缴费记录。

同时建设支撑上述业务的管理后台Web、住户小程序、商户小程序，以及平台账号权限、Project、文件、微信支付/退款/分账、最小积分、消息和上线支撑能力。

## 2.2 V1.0明确后移

- 社区活动与社群运营；
- 社区团购、拼团/社区集采；
- 运营作业小程序；
- 报事报修、投诉建议、物业工单、巡检等物业其他功能；
- 空间资源运营；
- 居民共享中的个人在线收款、平台资金托管、复杂二手电商售后；
- 邻里互助中的高风险个人服务、复杂排班/派单、平台代收代付；
- 停车场设备、闸机、车牌识别、车位实时占用等设备能力；
- 积分商城、签到、会员等级、复杂优惠券；
- 复杂仓储供应链、骑手调度；
- 复杂多级分账、商户钱包、自动提现；
- 模型驱动、低代码正式功能、AI语义识别、运维知识图谱和智能协同等课题创新点正式开发。

| Member微信会员 | A/B | 复用登录会员，扩展居民档案/房屋 |

| Mall Trade购物车/商品订单 | A/B | 商城直接复用 |

# 8. 微信支付与分账接入总体原则

## 8.1 关键结论

微信分账属于订单支付后的资金分配能力，不是“管理后台配置一个比例即可自动生效”的纯业务功能。V1.0需要同时建设业务配置、微信接口适配、异步结果管理、退款回退、解冻和对账。

平台后台负责业务规则配置；微信侧仍需完成分账产品开通、商户号/AppID关系、最大分账比例等外部配置。

## 8.2 接入模式技术验证

V1.0业务模型按“商户取得主要交易收入，平台按协议收取服务费/佣金”设计。

开发前必须验证以下两类模式并冻结最终方案：

1. **优先：平台收付通/服务商模式。** 更符合多商户平台型电商，由商户成为二级/特约收款主体，平台统一管理交易和抽佣；
2. **备选：普通商户分账模式。** 需验证谁作为分账方、谁作为接收方、多个商户号与小程序AppID绑定、API凭证管理以及最大分账比例。

> 不建议默认采用“平台普通商户统一收全款，再把大部分资金分给商户”的方式，因为普通商户分账存在最大分账比例限制，可能不适合平台商户获得主要交易收入的场景。

# 10. 微信分账执行与监管

## 10.1 支付时标记需分账

商城/收费服务订单若需要分账，在微信下单时必须传入“需分账”标识。非分账订单支付后不能再临时转为分账订单。

## 10.2 分账触发

一期默认：

- 商城订单：订单完成后触发；
- 服务订单：服务完成后触发；
- 退款处理中、售后未完成、订单异常时不得自动分账。

# 11. 退款与分账回退

## 11.1 未分账退款

未分账订单按业务退款规则调用Pay Refund，资金按微信规则从冻结资金等可用来源退款。

## 11.2 已分账退款

已完成分账的订单发生退款时：

```text
业务审核退款
→ 判断已分账金额
→ 判断是否需要分账回退
→ 发起分账回退/查询结果
→ 满足退款资金条件
→ 调用Pay Refund
→ 更新业务退款与分账回退状态
```

## 11.3 一期功能

| 功能 | 优先级 |
|---|---|
| 分账回退单 | S0 |
| 回退金额 | S0 |
| 回退商户号 | S0 |
| 回退结果 | S0 |
| PROCESSING查询 | S0 |
| 回退失败原因 | S0 |
| 回退与退款关联 | S0 |
| 回退记录查询 | S1 |

# 32. V1.0验收标准

## 32.1 商城（P1）

商户提交入驻资料 → Web审核/协议/授权 → 商品发布审核 → 居民购买并微信支付 → 商户备货/配送或核销 → 订单完成 → 微信分账最终成功 → 可完成基础退款/分账回退。

## 32.2 社区服务（P2）

服务发布审核 → 居民选择时间下单 → 收费服务支付 → 商户接单 → 到场 → 开始服务 → 完成 → 分账 → 可完成取消/退款；评价作为S1收口。

## 32.3 房屋绑定与物业缴费（P3）

居民微信登录 → 申请/确认绑定房屋 → 查询物业费账单 → 按规则选择积分抵扣（如启用） → 微信支付剩余金额 → 账单核销 → 缴费记录完整。

## 32.4 居民共享与邻里互助（P4）

实名认证/社区身份 → 发布闲置或互助/低风险技能内容 → Web审核 → 社区内展示 → 其他居民发起意向/认领/接单 → 双方线下完成 → 系统完成确认 → 可评价/举报。

一期验收不要求个人在线收款或资金托管。

## 32.5 停车缴费（P5）

居民维护/确认车辆 → 建立车辆/居民/停车关系 → 查询停车费账单 → 微信支付 → 支付回调核销账单 → 查询停车缴费记录。

一期验收不要求停车场设备接入、闸机控制或实时车位状态。

## 32.6 三端与上线

- 管理后台Web可完成平台审核、支付分账监管、物业/停车账单管理、居民共享/邻里内容审核和系统配置；
- 住户小程序可完成五条业务闭环对应的居民端操作；
- 商户小程序可完成商城/社区服务经营与履约；
- 11月中旬后完成五条闭环的全量回归、UAT、数据初始化和生产环境冒烟；
- **2026年11月30日前完成V1.0一期发布与验收。**
