# 1. 引言

## 1.1 编写目的

本文档用于明确《基于智慧社区数字化运营系统协同治理研究》课题的软件需求基线，说明课题系统需要解决的问题、支撑的业务场景、具备的业务中台与平台基础能力、两项创新技术对应的软件需求及研究验证要求，为后续概要设计、系统研发、测试验证和课题验收提供依据。

本文档定位为科技研发课题的需求规格说明书，不承担页面原型、按钮交互、数据库字段、接口参数和开发任务分解等详细设计职责。

## 1.2 项目背景

大光路老旧社区项目覆盖6个社区、18个老旧小区及34个服务点位，涉及5918户居民，总建筑面积约37.67万平方米，建筑年代主要集中于20世纪70—80年代。项目具有小区开放、片区零散、基础设施老化、物业管理基础薄弱、居民老龄化和多主体协同复杂等特征。

现有社区信息系统多围绕收费、报修、停车、门禁等单项业务建设，存在数据分散、业务割裂、跨主体协同依赖人工、项目重复开发和AI能力与实际业务脱节等问题。同时，大光路社区具有沿街商户、社区服务、闲置空间、活动组织和居民互助等运营基础，适合作为智慧社区数字化运营与协同治理技术的真实验证场景。

## 1.3 系统定位

本课题系统定位为面向智慧社区数字化运营与协同治理的技术研究及应用验证平台。系统以大光路社区为主要验证载体，兼顾办公楼宇、公寓、园区等业态的能力复用，重点研究：

1. 基于空间、组织、服务和业务对象模型的模型驱动配置；
2. 基于元数据、动态表单、流程与规则的低代码动态装配；
3. 运营主体、商品与服务、交易订单、任务履约、计费支付结算等核心业务中台能力复用；
4. 面向居民诉求的AI语义识别与事件结构化；
5. 基于工单、巡检、设备和维修记录的运维知识图谱；
6. 规则、知识与AI协同的派单辅助、案例推荐和风险提示。

系统不以覆盖大光路全部经营业务或建设完整商业SaaS产品为目标，而以典型业务场景验证平台化、配置化、智能化和可复制能力。

## 1.4 编制依据

1. 《基于智慧社区数字化运营系统协同治理研究》立项任务书；
2. 《平台通用能力》材料；
3. 大光路社区物业及运营功能规划讨论成果；

## 1.5 术语说明

| 术语 | 说明 |
|---|---|
| 模型驱动 | 通过空间、组织、服务和业务对象模型描述业务结构，并据此生成或约束系统能力 |
| 元数据 | 用于描述业务对象、字段、表单、流程、规则、权限和组件的信息 |
| 低代码动态装配 | 通过配置和组件组合形成业务应用，减少重复编码 |
| 场景模板 | 对某类业态或业务场景的模型、表单、流程、规则和权限配置进行封装的可复用模板 |
| 业务中台 | 沉淀运营主体、商品服务、交易订单、任务履约和计费支付结算等跨业务应用复用的领域对象和公共业务规则 |
| 平台基础能力 | 提供组织权限、流程、规则、表单、消息、文件、审计和任务调度等通用技术能力 |
| 运营主体 | 能够发布商品、服务、资源或活动并承担经营或履约责任的组织或个人 |
| 交易订单 | 记录购买对象、交易金额、支付状态和售后状态的公共交易单据 |
| 业务单据 | 记录服务预约、空间预约、活动报名等场景特有信息的单据 |
| 履约 | 商品配送、到店核销、上门服务、资源使用、活动签到等实际交付过程 |
| 社区事件 | 居民诉求、物业问题、巡检问题、设备告警等需要受理和处置的事项 |
| 运维知识图谱 | 对空间、设备、故障、事件、工单、人员、组织和维修方案等实体及关系进行组织的知识网络 |

# 2. 项目总体需求

## 2.1 建设目标

系统应形成一套智慧社区数字化运营与协同治理平台，满足以下目标：

1. 建立社区“人、房、事、物、组织”统一数据基础；
2. 保留并整合房屋、居民、报修投诉和工单等物业服务能力；
3. 支撑平台生态、空间资源、闲置交易、技能分享、社区活动等运营场景；
4. 建立可复用的运营主体、商品服务、交易订单、任务履约和计费支付结算能力，并由平台基础层提供统一身份、空间模型、流程规则等支撑；
5. 形成模型驱动、低代码动态装配和多项目快速复制能力；
6. 形成AI语义识别、运维知识图谱和智能协同能力；
7. 在大光路社区开展场景应用验证，并为其他社区、办公楼宇、公寓和园区复用提供基础。

## 2.2 研究目标

### 2.2.1 模型驱动与低代码动态装配研究目标

建立空间模型、组织模型、服务模型和业务对象模型，研究元数据驱动的动态表单、流程、规则、权限和组件装配机制。通过标准模板、项目参数和差异化配置，实现不同项目和业态的快速适配，降低重复开发工作量。

### 2.2.2 AI语义识别与运维知识图谱研究目标

面向居民报修、投诉、咨询、巡检和设备运维等场景，研究文本与语音诉求理解、意图识别、实体提取和事件结构化；基于历史工单、巡检、设备告警和维修记录构建运维知识图谱，支撑派单辅助、相似案例推荐、维修建议和风险提示。

### 2.2.3 场景应用与推广研究目标

以大光路社区的物业服务和运营场景为验证对象，评估平台能力、配置能力、AI能力和协同治理效果，形成可复制的模型、模板、能力组件、指标口径和实施方法。

## 2.3 建设原则

1. **课题研究优先。** 业务功能服务于关键技术验证，不追求一次性覆盖全部社区经营业务。
2. **分层能力复用。** 领域公共对象由业务中台统一管理，流程、规则和权限等由平台基础能力提供，业务应用按场景组织。
3. **统一模型、场景扩展。** 公共对象保持统一，场景特有信息通过业务单据或扩展模型承载。
4. **配置优先、代码兜底。** 高频变化的表单、流程、规则和模板采用配置；交易安全、金额计算和权限校验等核心逻辑由代码保障。
5. **AI辅助、人工负责。** AI结果应可解释、可校验、可修正，高风险事项由人工确认。
6. **数据最小必要。** 个人信息和敏感数据按业务必要性采集、授权使用和留痕审计。
7. **渐进建设。** 先实现核心闭环和验证能力，再逐步增强复杂交易、智能推荐和跨业态复制。

## 2.4 建设范围

### 2.4.1 业务应用范围

| 业务板块 | 本课题范围 |
|---|---|
| 物业服务 | 房屋及空间、居民档案、报修投诉、工单管理 |
| 平台生态运营 | 运营主体、商户、商品发布与商城运营、社区团购、服务发布、服务预约、积分与运营激励 |
| 空间与资源运营 | 空间资源、资源预约、使用记录 |
| 闲置交易运营 | 闲置发布、信息审核、交易管理 |
| 技能分享与邻里服务 | 技能认证、服务发布、服务评价 |
| 社区活动与社群运营 | 活动管理、报名管理、社群运营 |
| 数据运营分析 | 运营统计、服务分析、社区治理分析 |

### 2.4.2 技术研究范围

- 统一空间、组织、服务和业务对象建模；
- 元数据、动态表单、流程、规则和权限配置；
- 场景模板、版本发布、差异化扩展和多项目复制；
- 文本与语音诉求理解、事件结构化和人工校验；
- 运维知识抽取、知识图谱、相似案例和派单辅助；
- 平台事件、业务留痕、指标口径和验证数据采集。

### 2.4.3 非研究范围

以下内容不作为本课题独立业务方向或完整产品建设目标：

- 自营及联合运营；
- 政府及公共服务；
- 碳普惠运营；
- 复杂仓储、供应链和跨区域物流平台；
- 完整金融级清分清算体系；
- 大规模物联网接入平台；
- 医疗诊断、护理决策等高风险专业系统；
- 以按钮、页面和数据库字段为粒度的详细设计。

## 2.5 需求层级与课题研究关联

第6章对各业务应用采用统一格式描述，是为了形成完整、可追溯的需求基线，不代表所有业务模块具有相同的研发优先级和研究权重。课题需求按以下层级控制：

| 层级 | 内容 | 课题定位 | 建设要求 |
|---|---|---|---|
| R0 核心研究能力 | 模型驱动、低代码动态装配、AI语义识别、运维知识图谱、智能协同 | 两个创新点的直接载体 | 必须完成技术方案、原型能力和验证证据 |
| R1 核心验证场景 | 居民报修与工单、服务预约、空间预约、活动报名 | 验证模型、流程、订单调用和AI协同 | 形成可运行的端到端闭环 |
| R2 基础复用能力 | 运营主体、商品服务、交易订单、任务履约、计费支付结算，以及统一身份、空间模型和数据指标 | 为多个场景提供公共支撑 | 统一设计，按验证需要建设必要深度 |
| R3 扩展验证场景 | 闲置交易、技能分享、社群运营及更复杂的营销交易 | 验证平台扩展性和后续产品方向 | 可完成需求设计、轻量原型或阶段性实现 |
| R4 既有能力承接 | 收费、停车、巡检及既有物业基础功能 | 任务书要求的平台协同基础和数据来源 | 优先复用或集成，不重复建设完整系统 |

课题验收应优先评价R0和R1层的技术成果与验证效果，不以普通物业或运营功能的数量作为创新成果完成度的主要依据。

# 3. 用户与角色需求

## 3.1 居民用户

居民用户包括业主、住户、租客及其家庭成员。居民应能够完成身份认证与房屋关联，提交报修投诉，查询工单进度，浏览和购买社区商品、参与社区团购、预约社区服务和空间资源、使用及获取积分、发布闲置物品或技能、报名活动并进行评价。

针对老年居民，系统应提供简化入口、清晰文字、语音输入和人工代办渠道，并允许经授权的家庭成员协助办理。

## 3.2 物业工作人员

物业工作人员包括客服、管家、维修、巡检和项目管理人员。其应能够维护基础资源，受理居民诉求，创建和处置工单，记录巡检与维修过程，并在授权范围内协助运营业务处理。

## 3.3 社区工作人员

社区工作人员主要参与社区事件协同、活动组织、居民沟通和服务监督。系统应依据项目合作边界配置其可见数据和可操作事项，不默认赋予跨组织管理权限。

## 3.4 商户及服务主体

商户、服务机构和个人服务提供者应能够按准入要求提交主体、资质和服务资料，维护可提供的商品或服务，接收预约或订单，完成履约并查看评价。个人服务提供者仅可发布平台允许的低风险服务。

## 3.5 平台运营人员

平台运营人员负责主体准入、商品与服务类目及内容审核、商城与团购运营、积分规则、活动运营、资源开放、交易监控、投诉处置、规则配置和运营分析。不同项目的运营人员只可管理授权项目及其数据。

## 3.6 系统管理员

系统管理员负责组织、角色、权限、字典、参数、接口、日志、模板和发布管理。系统管理员不应默认拥有业务敏感数据的无限制查看权限，特殊查询应留痕。

## 3.7 课题研究与评估人员

研究人员应能够在脱敏和授权范围内查看验证指标、样本标注结果、AI识别效果、配置发布记录和场景运行数据，用于课题研究、阶段评估和成果总结。

## 3.8 权限与数据范围

系统应支持“用户—组织—角色—项目—空间—数据对象”组合授权。居民只能访问本人及被授权家庭成员的数据；商户和服务主体只能访问本主体业务数据；物业、社区和平台运营人员按项目、空间和职责范围访问数据；研究人员原则上使用脱敏数据。

# 4. 典型业务验证场景

## 4.1 居民诉求与物业协同

居民通过文字、语音、图片或人工代录提交报修、投诉和咨询。系统识别诉求类型、位置、对象和紧急程度，生成结构化事件或工单草稿，经人工确认后流转至责任人员，完成受理、派单、处置、回访和评价闭环。

## 4.2 巡检与设备运维

物业人员执行巡检时记录设备状态和问题，异常可转为工单。系统关联设备、空间、故障、工单、维修人员和维修方案，逐步沉淀运维知识，验证相似故障检索、维修建议和风险提示。

## 4.3 平台生态运营

商户、服务机构或其他运营主体完成入驻认证后，可根据经营范围发布实物商品、社区团购或预约型服务。居民可在统一小程序中完成商品购买、团购参与或服务预约，并调用商品服务、交易订单、计费支付结算、任务履约及积分运营等公共能力形成业务闭环。

其中，商品购买重点验证商品规格、库存、订单、支付、配送或自提；社区团购重点验证团购活动、成团规则、团购订单及核销履约；服务预约重点验证时间库存、服务预约单、支付和任务履约。该场景用于验证多种供给形态在统一运营主体和公共能力基础上的组合复用。

## 4.4 空间资源预约

运营人员将活动室、会议室或其他可开放资源配置为可预约对象，设置时段、容量、审核和收费规则。居民或机构提交预约，系统进行冲突校验、审核、支付或免费确认、签到核销和使用记录。

## 4.5 社区活动运营

运营人员发布老年、亲子、文化或便民活动，配置场次、名额、报名对象和收费方式。居民报名后完成审核、支付、签到和评价。免费活动只形成报名记录，付费活动同时关联交易订单。

## 4.6 居民共享运营

居民在实名认证后发布闲置物品或低风险技能服务。平台完成内容审核、社区范围展示、供需撮合、交易或预约、评价和举报处理，用于验证居民作为供给主体时的信用与风控机制。

## 4.7 多业态复制验证

选择社区服务预约、空间预约或活动报名等通用场景，将大光路配置复制到办公楼宇或公寓模拟项目，通过替换空间结构、用户身份、服务目录和规则参数验证复用效果，不要求完整建设办公楼或公寓业务系统。

# 5. 总体功能结构

## 5.1 业务应用层

业务应用层面向具体用户和完整业务流程，包括物业服务、平台生态运营、空间与资源运营、闲置交易运营、技能分享与邻里服务、社区活动与社群运营、数据运营分析。

## 5.2 核心业务中台层

业务中台只保留具有明显跨场景复用、独立生命周期、统一状态或数据一致性要求的领域能力，精简为以下五项：

| 核心业务中台 | 主要能力 | 主要服务场景 |
|---|---|---|
| 运营主体中台 | 商户、服务机构和个人服务者的建档、认证、资质、服务范围和状态 | 平台生态、技能服务、订单、履约和结算 |
| 商品与服务中台 | 类目、商品、标准服务、预约服务、闲置物品、技能服务、规格、价格和可售条件 | 商城、社区团购、服务发布、闲置交易、技能服务及各类预约 |
| 交易订单中台 | 公共订单、订单项、交易快照、金额、公共状态、取消和退款申请 | 商城购物、社区团购、服务预约、资源预约、闲置交易、技能服务及付费活动 |
| 任务履约中台 | 工单或履约任务、派单、接单、转派、到场、处理、SLA、异常和结果回传 | 物业工单、巡检维修、社区服务和技能服务 |
| 计费支付结算中台 | 收费项目、计费规则、应收账单、支付、退款、核销、对账和基础结算 | 物业收费、收费服务、资源预约和交易场景 |

以下能力不再作为独立业务中台：

- 用户、账号、组织和权限归入平台基础能力；
- 空间树和空间关系归入空间基础模型，具体资源预约归业务应用；
- 活动、场次、报名、签到和社群归社区活动与社群运营应用；
- 合同采用业务模块轻量记录或复用现有合同系统；
- 积分与基础运营权益作为贯穿商城、团购、服务、活动和空间等场景的横向运营能力建设，暂不单独建设复杂营销权益中台；
- 评价事实随订单或任务保存，投诉违规由业务应用处理，风险分析归数据与AI能力；
- 数据运营和课题验证指标归入数据与AI能力层。

## 5.3 平台基础能力层

平台基础能力包括：

- 统一账号、人员、组织与权限；
- 空间基础模型及人、房、组织、设备关系；
- 参数字典与元数据；
- 动态表单；
- 流程引擎；
- 规则引擎；
- 场景模板与组件装配；
- 消息中心、文件中心、审计日志；
- 平台事件、接口管理和任务调度。

平台基础能力提供通用技术支撑，不承载订单金额、任务履约、支付退款等领域业务规则。

## 5.4 数据与AI能力层

数据与AI能力层包括：

- 数据运营与研究验证中心；
- 业务指标、专题分析和研究证据；
- 语音转写、文本预处理、意图识别和实体提取；
- 事件结构化；
- 运维知识抽取与知识图谱；
- 派单辅助、相似案例、维修建议和风险提示；
- AI修订、推荐采纳及课题验证数据。

## 5.5 功能协同原则

业务应用负责场景化交互、业务前置校验、流程编排和场景特有信息；五项核心业务中台负责跨应用复用的领域对象及公共规则；平台基础能力负责身份、空间、表单、流程、规则和通用技术支撑；数据与AI能力负责分析、识别、知识和智能协同。

各层通过标准服务接口和业务事件协同，不直接修改其他模块的数据。前端调用业务应用接口，由业务应用编排中台能力，不由前端直接串联多个中台接口。

# 6. 业务应用功能需求

## 6.1 物业服务

### 6.1.1 房屋及空间管理

#### （1）功能概述

房屋及空间管理用于建立社区、小区、楼栋、单元、房屋和公共区域的统一空间基础，为居民身份、物业服务、资源运营、事件定位和多业态复制提供支撑。

#### （2）业务需求

- 支持符合大光路开放式小区和零散片区特点的多层级空间结构；
- 支持房屋、公共区域、服务点位和设备位置关联；
- 支持空间节点的创建、调整、合并、拆分和停用；
- 支持不同项目按模板建立不同的空间层级；
- 空间变更后应保持历史业务可追溯。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.1.1-01 | 空间树管理 | 支持按项目配置社区、小区、楼栋、单元、房屋和公共区域等空间节点 |
| FR-6.1.1-02 | 房屋档案 | 维护房屋编码、地址、面积、用途、状态及所属空间 |
| FR-6.1.1-03 | 公共空间管理 | 维护公共区域、服务点位及其用途和管理主体 |
| FR-6.1.1-04 | 空间关系维护 | 建立空间与居民、组织、设备、资源及工单的关联 |
| FR-6.1.1-05 | 空间变更留痕 | 对节点调整、合并、拆分和停用保留版本及操作记录 |

#### （4）数据需求

核心数据对象包括项目、空间节点、房屋、公共区域、空间类型、空间状态、空间关系和空间变更记录。

#### （5）业务规则

- 同一项目内空间编码应唯一；
- 房屋必须归属有效空间节点；
- 已被业务引用的空间不得物理删除；
- 空间调整不得破坏历史工单、订单和居民关系；
- 跨项目空间数据默认隔离。

### 6.1.2 居民档案

#### （1）功能概述

居民档案用于统一管理自然人账户、居民身份、家庭关系和房屋关系，为物业服务、运营服务和适老化协助办理提供身份基础。

#### （2）业务需求

- 支持手机号、微信等账号与统一自然人实体关联；
- 支持业主、住户、租客和家庭成员等身份；
- 支持一人多房、一房多人及身份有效期；
- 支持家庭成员授权代办；
- 按最小必要原则维护联系信息和服务偏好。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.1.2-01 | 居民档案管理 | 建立和维护居民基础档案及状态 |
| FR-6.1.2-02 | 账号映射 | 将手机号、微信标识等多端账号映射至统一用户 |
| FR-6.1.2-03 | 房屋关系认证 | 建立居民与房屋之间的业主、住户、租客等关系 |
| FR-6.1.2-04 | 家庭关系与授权 | 支持家庭成员关联及代办授权 |
| FR-6.1.2-05 | 标签与偏好 | 记录经授权使用的服务偏好和运营标签 |

#### （4）数据需求

核心数据对象包括用户、账号、居民身份、房屋关系、家庭关系、授权记录、联系信息、标签及用户同意记录。

#### （5）业务规则

- 居民与房屋关系应经过资料、物业或规则校验；
- 授权应明确范围、期限和撤销方式；
- 敏感信息应按角色脱敏展示；
- 标签不得用于超出授权范围的用途；
- 关系失效后历史业务记录仍应可追溯。

### 6.1.3 报修投诉

#### （1）功能概述

报修投诉用于统一受理居民通过文字、语音、图片或人工代录提交的报修、投诉、建议和咨询，是AI语义识别和社区事件协同的主要入口。

#### （2）业务需求

- 支持居民自助、电话代录和现场代录；
- 支持关联房屋、公共区域、设备和服务事项；
- 支持AI提取事件类型、位置、对象和紧急程度；
- 支持人工校验AI结果；
- 支持查询受理进度、结果反馈和评价。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.1.3-01 | 多渠道诉求提交 | 支持文本、语音、图片、附件及人工代录 |
| FR-6.1.3-02 | 诉求分类 | 支持人工选择或AI推荐报修、投诉、建议、咨询等类型 |
| FR-6.1.3-03 | 事件定位 | 关联项目、空间、房屋、设备或服务对象 |
| FR-6.1.3-04 | 受理与转办 | 对诉求进行受理、补充、退回、转工单或协同转办 |
| FR-6.1.3-05 | 进度与反馈 | 向居民展示节点进度、处理结果并收集评价 |

#### （4）数据需求

核心数据对象包括居民诉求、输入文本、语音及附件、事件类型、空间位置、关联对象、AI识别结果、人工修订记录、受理记录和反馈评价。

#### （5）业务规则

- AI识别结果不得直接覆盖居民原始表述；
- 低置信度、高风险和信息不完整事件必须人工确认；
- 投诉信息按职责范围控制可见性；
- 重复诉求可关联但不得无依据关闭；
- 从诉求转工单后应保持双向关联。

### 6.1.4 工单管理

#### （1）功能概述

工单管理用于承接报修、投诉、巡检问题和设备告警的处置过程，形成创建、分派、接单、处理、挂起、完结、回访和评价闭环。

#### （2）业务需求

- 支持人工、诉求转换、巡检转换和告警触发创建工单；
- 支持按类型、空间、技能、责任组织和时效进行派单；
- 支持转派、退回、协同、挂起和升级；
- 支持处置过程和证据留痕；
- 支持AI派单建议和相似案例推荐。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.1.4-01 | 工单创建 | 从多种来源生成工单并记录来源关系 |
| FR-6.1.4-02 | 分派与接单 | 支持人工、规则和AI辅助分派及接单 |
| FR-6.1.4-03 | 协同处置 | 支持转派、协办、退回、挂起、催办和升级 |
| FR-6.1.4-04 | 过程记录 | 记录到场、处理说明、附件、材料和完成结果 |
| FR-6.1.4-05 | 时效管理 | 配置响应和处理时限并触发提醒或升级 |
| FR-6.1.4-06 | 完结与回访 | 完成审核、居民确认、回访和评价 |

核心数据对象包括工单、工单来源、事件类型、责任组织、处理人员、状态流转、时效规则、过程记录、附件、评价和回访记录。

#### （5）业务规则

- 工单状态变化必须通过合法操作触发，不得直接修改状态字段；
- 派单建议仅作为辅助，责任人员由有权主体确认；
- 挂起和退回必须填写原因；
- 完结需满足必填处置记录和证据要求；
- 超时、转派和关键状态变化应保留审计记录。

## 6.2 平台生态运营

平台生态运营是智慧社区数字化运营平台的核心业务应用之一，围绕“运营主体入驻—供给发布—居民消费与参与—交易支付—配送/核销/服务履约—评价与积分激励”形成完整运营闭环。

平台应支持商户、服务机构及个人服务提供者等不同运营主体，在完成认证并取得相应经营范围后，按业务类型发布实物商品、社区团购和预约型服务。商城、团购和服务并非三套独立系统，而是在统一运营主体、商品与服务、交易订单、计费支付结算及积分运营能力基础上形成不同业务场景。

### 6.2.1 运营主体管理

#### （1）功能概述

运营主体管理用于统一管理能够提供商品、服务或活动的商户、服务机构和个人服务提供者，建立主体身份、资质、经营范围和信用档案，为商城、团购、服务及后续其他运营场景提供可信主体基础。

#### （2）业务需求

- 支持组织主体和个人主体分类准入；
- 支持主体、门店、服务人员和项目范围关联；
- 支持资质、合同、有效期和经营范围管理；
- 支持按经营范围控制可发布的商品、团购及服务类目；
- 支持不同项目对同一主体进行合作授权；
- 支持主体经营、履约质量、评价和违规记录汇总。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.2.1-01 | 主体建档 | 建立商户、机构和个人服务提供者档案 |
| FR-6.2.1-02 | 主体认证 | 完成实名认证、组织认证和准入审核 |
| FR-6.2.1-03 | 资质管理 | 维护证照、保险、专业资格及有效期 |
| FR-6.2.1-04 | 经营范围 | 配置可发布商品、团购、服务的类目、区域和项目范围 |
| FR-6.2.1-05 | 人员关联 | 维护主体所属经营人员、服务人员及其技能 |
| FR-6.2.1-06 | 主体信用 | 汇总订单履约、评价、投诉、退款和违规记录 |

#### （4）数据需求

核心数据对象包括运营主体、主体类型、门店、人员、资质、经营范围、项目授权、认证记录、信用记录和合作状态。

#### （5）业务规则

- 主体认证通过后方可发布经营内容；
- 商品、团购和服务发布范围不得超出主体准入类目；
- 专业服务必须校验所需资质及有效期；
- 个人主体不得发布平台限制的高风险商品或服务；
- 主体、履约主体和收款主体允许不同，但必须明确关系；
- 主体停用后不得新增交易，历史订单、售后和结算记录应保留。

### 6.2.2 商户管理

#### （1）功能概述

商户管理面向大光路周边门店和社区商业，支持商户入驻、门店展示、经营配置、合作关系和运营监管，为居民建立可信的社区商业和本地生活服务入口。

#### （2）业务需求

- 支持商户申请、运营审核和项目入驻；
- 支持一家主体管理多个门店；
- 支持按项目和社区配置门店可见范围；
- 支持商户配置商品销售、社区团购、到店核销、配送、自提及服务预约等经营方式；
- 支持商户经营状态、服务质量和违规处置；
- 支持商户商品、团购、服务、订单、评价和经营数据查询。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.2.2-01 | 商户入驻 | 提交主体、门店、经营类目和联系人资料 |
| FR-6.2.2-02 | 门店档案 | 维护地址、营业时间、展示信息、配送及服务范围 |
| FR-6.2.2-03 | 合作关系 | 关联项目合作状态、协议和有效期 |
| FR-6.2.2-04 | 经营配置 | 配置商品、团购、服务类目及配送、自提、核销、上门等履约方式 |
| FR-6.2.2-05 | 经营监管 | 执行暂停、整改、恢复和退出处理 |
| FR-6.2.2-06 | 经营概览 | 展示商品、团购、服务、订单、履约、评价和投诉概况 |

#### （4）数据需求

核心数据对象包括商户主体、门店、项目入驻关系、经营类目、展示信息、营业状态、履约方式、合同引用、监管记录和经营指标。

#### （5）业务规则

- 商户展示名称、经营类目和资质信息应与认证资料一致；
- 超出准入范围的商品、团购和服务不得发布；
- 合作或资质到期应触发提醒并按规则限制经营；
- 商户退出不影响已产生订单的履约、售后和结算；
- 商户数据按主体与项目授权隔离。

### 6.2.3 商品发布与商城运营

#### （1）功能概述

商品发布与商城运营用于支持认证商户发布实物商品，并面向居民形成社区商城的浏览、下单、支付、配送或自提、核销、评价和售后基础闭环。

商城重点服务社区生鲜、米面粮油、生活日用、餐饮套餐及周边商户精选商品等本地消费场景，不建设复杂仓储供应链和大型综合电商平台。

#### （2）业务需求

- 支持商品类目、商品、SKU、价格、库存和展示信息配置；
- 支持商户发布、平台审核、上架、下架和暂停销售；
- 支持居民按分类、商户和推荐专区浏览商品；
- 支持商品直接购买及基础购物车能力；
- 支持配送、社区自提和到店核销等基础履约方式；
- 支持订单取消、退款、评价和基础售后；
- 支持商品购买获取积分和按规则使用积分抵扣。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.2.3-01 | 商品类目 | 建立社区商品多级分类及可经营主体范围 |
| FR-6.2.3-02 | 商品管理 | 维护商品名称、图片、说明、所属商户、品牌及展示信息 |
| FR-6.2.3-03 | 商品规格 | 配置SKU、单位、规格属性、售价和库存 |
| FR-6.2.3-04 | 上架审核 | 支持商品提交审核、上架、下架、暂停和版本留痕 |
| FR-6.2.3-05 | 商城展示 | 支持精选、分类、商户商品、搜索和推荐展示 |
| FR-6.2.3-06 | 购买下单 | 支持直接购买及基础购物车，生成公共交易订单 |
| FR-6.2.3-07 | 配送与核销 | 支持配送、自提或到店核销等基础履约方式 |
| FR-6.2.3-08 | 售后评价 | 支持取消、退款申请、收货/核销确认和商品评价 |
| FR-6.2.3-09 | 积分联动 | 支持按规则计算消费积分、积分抵扣及订单完成后积分发放 |

#### （4）数据需求

核心数据对象包括商品类目、商品、SKU、商品价格、普通库存、商品图片、发布状态、商户引用、履约方式、购物车明细、订单引用、退款引用、评价和积分记录。

#### （5）业务规则

- 商品发布主体必须具备对应经营范围；
- 商品审核通过且处于有效上架状态后方可购买；
- 下单时应保存商品、价格、商户和履约方式快照；
- 商品库存占用、支付失败、取消和退款应按规则释放库存；
- 首期不建设跨商户复杂拆单、复杂促销、仓储调拨和供应链体系；
- 积分抵扣不得造成订单应付金额低于平台配置的最小支付要求；
- 商品下架不得影响已产生订单的履约和售后。

### 6.2.4 社区团购运营

#### （1）功能概述

社区团购运营用于支持平台或认证商户围绕社区居民集中消费需求发起团购活动，通过团购价格、活动周期、成团规则和社区自提/配送等方式形成具有社区特色的商业运营场景。

团购活动负责表达成团条件和运营规则，实际交易金额、支付和退款仍由公共交易订单及计费支付结算能力统一承接。

#### （2）业务需求

- 支持平台或商户发起商品团购及服务套餐团购；
- 支持配置团购商品、活动时间、团购价格、原价、限购和适用项目；
- 支持按人数、数量或其他简单规则设置成团条件；
- 支持居民开团、参团或直接参加平台统一团；
- 支持团购进度、剩余时间、已参团人数和成团状态展示；
- 支持成团成功后的配送、自提、到店核销或服务履约；
- 支持未成团自动关闭并按规则退款；
- 支持团购完成后的积分发放和评价。

#### （3）功能需求

|---|---|---|
| FR-6.2.4-01 | 团购活动创建 | 配置活动名称、商品/服务、发起主体、适用项目和活动时间 |
| FR-6.2.4-02 | 团购规则 | 配置团购价、成团人数/数量、限购、库存和参与条件 |
| FR-6.2.4-03 | 团购发布 | 支持审核、发布、暂停、结束和活动状态管理 |
| FR-6.2.4-04 | 开团与参团 | 支持居民发起团、参与已有团或参加平台统一团 |
| FR-6.2.4-05 | 团购进度 | 展示参团人数、剩余名额、倒计时和当前成团状态 |
| FR-6.2.4-06 | 团购订单 | 参与团购后生成公共交易订单并完成支付 |
| FR-6.2.4-07 | 成团处理 | 达到条件后确认成团并进入后续履约 |
| FR-6.2.4-08 | 失败关闭 | 活动结束未成团时关闭团购并按规则发起退款 |
| FR-6.2.4-09 | 履约核销 | 支持配送、自提、到店核销或服务预约等履约方式 |
| FR-6.2.4-10 | 积分与评价 | 团购完成后发放积分并支持居民评价 |

#### （4）数据需求

核心数据对象包括团购活动、团购规则、团购商品/服务、活动库存、团购团队、参团记录、成团条件、团购状态、订单引用、支付引用、履约方式、退款记录、积分记录和评价。

#### （5）业务规则

- 团购发起主体必须具备相应商品或服务经营资格；
- 团购活动开始后，影响已参团用户权益的关键规则不得无痕修改；
- 团购库存不得超过对应商品或服务的有效可售数量；
- 成团条件达到后应按规则锁定成团结果，不因后续普通退出自动失效；
- 未成团订单应按规则取消并发起退款；
- 团购活动单与公共交易订单保持职责分离；
- 首期以简单成团、限时团购和社区集中采购为主，不建设复杂多级团长分销体系。

### 6.2.5 服务发布

#### （1）功能概述

服务发布用于将家政、维修、清洗、助老、养老、培训等线下服务标准化为可查询、可预约和可履约的服务商品。

#### （2）业务需求

- 支持服务类目、服务项目和服务规格配置；
- 支持固定价、按时长、按数量及询价等方式；
- 支持配置服务区域、可预约时间和履约方式；
- 支持审核、上架、下架和版本留痕；
- 支持助老、养老、社区餐饮等服务由机构或商户按资质范围发布；
- 支持多项目复用标准服务模板；
- 支持服务完成后积分奖励和评价激励。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.2.5-01 | 服务类目 | 建立多级服务分类及风险等级 |
| FR-6.2.5-02 | 服务项目 | 配置名称、说明、主体、适用对象和履约标准 |
| FR-6.2.5-03 | 服务规格 | 配置时长、次数、人数、面积等服务SKU |

#### （4）数据需求

核心数据对象包括服务类目、服务项目、服务SKU、价格规则、服务范围、时间库存、履约标准、风险等级、发布版本、审核记录和积分规则引用。

#### （5）业务规则

- 服务发布主体必须具备相应经营范围和有效资质；
- 影响价格和履约的变更不得改变历史订单快照；
- 高风险服务应限制主体类型并增加人工审核；
- 可预约数量不得超过时间库存和人员容量；
- 项目可继承标准服务模板并形成差异化配置；
- 积分仅在符合规则的有效履约和评价行为后发放。

### 6.2.6 服务预约

#### （1）功能概述

服务预约用于承载居民选择服务、规格、服务对象、时间和地址后的场景特有信息，并与统一交易订单、支付、任务履约和积分能力协同形成闭环。

#### （2）业务需求

- 支持居民自助预约和工作人员代客预约；
- 支持居民本人及经授权家庭成员作为服务对象；
- 支持时间、地址、人员和服务范围校验；
- 支持免费预约、在线支付或线下确认；
- 支持改期、取消、接单、上门、完成和评价；
- 支持履约完成和评价后按规则发放积分；
- 保持服务预约单与公共交易订单职责分离。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |

#### （5）业务规则

- 服务预约单记录场景特有信息，交易订单记录金额、支付和售后；
- 免费预约可不生成交易订单；
- 收费预约在支付结果确认后方可进入约定履约阶段；
- 取消或退款应同步释放时间库存；
- 家庭代办必须存在有效授权关系；
- 重复请求应通过幂等机制避免重复预约和重复扣款；
- 积分发放应基于有效完成的业务事实，不因取消或退款订单重复发放。

### 6.2.7 积分与运营激励

#### （1）功能概述

积分与运营激励用于通过统一积分账户和基础积分规则，将居民在商城消费、社区团购、服务履约、活动参与、空间使用和评价互动等行为形成可持续的运营激励机制，提高居民活跃度和重复参与率。

本功能作为跨运营场景的横向能力建设，不单独建设复杂营销权益中台。

#### （2）业务需求

- 支持居民统一积分账户和余额查询；
- 支持签到、消费、团购、服务完成、活动签到、空间使用和评价等积分获取场景；
- 支持商城、团购及指定服务使用积分抵扣；
- 支持积分兑换商品、服务优惠或社区权益；
- 支持积分任务、积分明细和兑换记录；
- 支持积分规则按项目、业务类型和有效期配置；
- 支持撤销、退款或异常业务对应的积分回退；
- 支持后续与会员等级、优惠券等运营权益扩展。

#### （3）功能需求

|---|---|---|
| FR-6.2.7-01 | 积分账户 | 为居民维护统一积分余额、累计获得和累计使用数据 |
| FR-6.2.7-02 | 积分规则 | 配置签到、消费、服务、活动、空间、评价等积分获取规则 |
| FR-6.2.7-03 | 积分发放 | 根据有效业务事件自动或人工确认后发放积分 |
| FR-6.2.7-04 | 积分抵扣 | 支持商城、团购和指定服务订单按规则使用积分抵扣 |
| FR-6.2.7-05 | 积分兑换 | 支持积分兑换商品、优惠权益或社区服务权益 |
| FR-6.2.7-06 | 积分任务 | 展示签到、消费、参与活动等可完成的积分任务 |
| FR-6.2.7-07 | 积分明细 | 查询积分来源、使用、回退、失效和当前余额 |
| FR-6.2.7-08 | 积分回退 | 在退款、取消或业务撤销时按原规则回退已发放或已抵扣积分 |

#### （5）业务规则

- 积分变动必须关联明确业务来源或人工调整依据；
- 同一业务事件不得重复发放积分；
- 退款、取消和撤销应按规则处理已发放和已使用积分；
- 积分抵扣比例、上限和适用范围应可配置；
- 积分不等同于现金账户，不提供提现和自由转账能力；
- 积分规则变更不得无痕修改历史流水；
- 涉及异常调整时应记录操作人、原因和审计信息。

## 6.3 空间与资源运营

### 6.3.1 空间资源管理

#### （1）功能概述

空间资源管理用于将活动室、会议室、服务场地、停车位等可开放资源形成可预约、可核销、可统计的运营对象。

#### （2）业务需求

- 支持从空间基础数据中选择可运营资源；
- 支持资源权属、管理主体和开放范围；
- 支持按时段、容量或数量配置可用资源；
- 支持免费、按次、按时和长期使用等规则；
- 支持在社区、办公楼和公寓场景中复用。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|

| FR-6.3.1-02 | 权属与管理 | 维护权属、管理主体、运营权限和责任人 |
| FR-6.3.1-03 | 开放计划 | 配置开放日期、时段、容量和暂停开放 |
| FR-6.3.1-04 | 使用规则 | 配置对象限制、审核、收费、取消和违约规则 |
| FR-6.3.1-05 | 状态管理 | 管理可用、占用、维护、冻结和停用状态 |

#### （4）数据需求

核心数据对象包括资源、资源类型、空间引用、权属主体、管理主体、开放计划、时间库存、价格规则、使用规则和资源状态。

#### （5）业务规则

- 仅具有运营权限的资源方可对外开放；

- 同一资源同一时段不得重复占用；
- 权属不清或安全条件不满足的资源不得上线；
- 资源特有属性可扩展，但核心时段和状态数据应结构化存储。

#### （1）功能概述

资源预约用于居民、商户或机构申请使用指定资源和时段，并完成冲突校验、审核、收费、取消和入场准备。

#### （2）业务需求

- 支持按日历查询资源可用时段；
- 支持个人和组织申请；
- 支持即时确认或人工审核；
- 支持免费预约和收费预约；
- 支持改期、取消、候补及超时释放。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |

| FR-6.3.2-03 | 冲突与资格校验 | 校验时段占用、用户资格、容量和使用限制 |

#### （5）业务规则

- 预约确认前应完成资格、时间和容量校验；
- 库存锁定、支付和确认应具备超时释放机制；
- 付费预约取消应按规则联动退款；
- 审核驳回必须记录理由；
- 一笔预约只对应一个明确的资源使用范围。

### 6.3.3 使用记录

#### （1）功能概述

使用记录用于确认资源是否按约使用，记录签到、核销、异常、损坏和完成情况，为利用率、收益和责任追溯提供依据。

#### （2）业务需求

- 支持二维码、验证码或人工确认入场；
- 支持记录实际使用起止时间；
- 支持异常占用、超时、取消和未到场；
- 支持记录设施损坏及后续处理；
- 支持按资源和项目统计使用情况。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |

| FR-6.3.3-03 | 异常登记 | 记录未到场、超时、违规和资源故障 |
| FR-6.3.3-04 | 完成确认 | 完成使用交接并更新资源状态 |
| FR-6.3.3-05 | 使用统计 | 汇总预约率、核销率、利用率和异常情况 |

#### （4）数据需求

核心数据对象包括使用记录、核销凭证、实际使用时间、异常类型、现场附件、损坏记录、交接结果和统计指标。

#### （5）业务规则

- 仅有效预约可正常核销；
- 核销凭证应防止重复使用；
- 使用结束后资源状态方可释放；
- 损坏和重大异常应可关联工单；
- 利用率统计口径应区分开放时长、预约时长和实际使用时长。

## 6.4 闲置交易运营

### 6.4.1 闲置发布

#### （1）功能概述

闲置发布用于实名认证居民在所属社区范围内发布出售、赠送、交换或短期租借的闲置物品，形成社区居民之间的循环利用入口。

#### （2）业务需求

- 支持居民发布物品图片、说明、新旧程度和交易方式；
- 支持按社区或项目控制可见范围；
- 支持一件一库存的闲置物品特征；
- 支持草稿、待审核、已发布、已锁定和已下架状态；
- 支持与旧物回收等合作场景扩展。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.4.1-01 | 闲置建档 | 录入物品类别、名称、图片、说明和成色 |
| FR-6.4.1-02 | 交易方式 | 支持出售、赠送、交换和租借等方式 |
| FR-6.4.1-03 | 价格与交付 | 配置价格、是否议价及社区内交付方式 |
| FR-6.4.1-04 | 可见范围 | 按项目、社区或身份控制展示范围 |
| FR-6.4.1-05 | 发布状态 | 管理草稿、审核、发布、锁定、成交和下架 |

#### （4）数据需求

核心数据对象包括闲置物品、发布者、物品类别、图片、描述、价格、交易方式、可见范围、库存状态和发布状态。

#### （5）业务规则

- 发布者必须完成实名认证和社区身份校验；
- 禁止发布物品清单应可配置；
- 闲置物品默认库存为一，成交或锁定后不可重复下单；
- 居民不得以闲置名义开展未获准的持续经营；
- 发布者应可主动下架未进入交易的物品。

### 6.4.2 信息审核

#### （1）功能概述

信息审核用于对居民发布的文字、图片、类别和交易方式进行规则或人工审核，降低违法违规内容、虚假信息和社区交易风险。

#### （2）业务需求

- 支持关键词、图片和类别规则初筛；
- 支持人工通过、驳回、要求修改和下架；
- 支持居民举报后的复核；
- 支持记录审核依据和操作人员；
- 支持高风险类别禁止发布。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.4.2-01 | 自动初筛 | 根据关键词、类别和风险规则标记异常内容 |
| FR-6.4.2-02 | 人工审核 | 对待审信息执行通过、驳回或退回修改 |
| FR-6.4.2-03 | 举报复核 | 受理居民举报并对已发布内容复核 |
| FR-6.4.2-04 | 强制下架 | 对违规、争议或存在安全风险的信息执行下架 |
| FR-6.4.2-05 | 审核留痕 | 保存审核结果、理由、证据和处理记录 |

#### （4）数据需求

核心数据对象包括审核任务、风险标签、命中规则、审核意见、举报记录、处理证据、下架原因和申诉记录。

#### （5）业务规则

- 命中明确禁止规则的信息不得发布；
- 自动审核不确定的内容应转人工处理；
- 审核结论应与具体版本绑定；
- 举报人和被举报人信息应按权限隔离；
- 申诉处理不得覆盖原审核和处置记录。

### 6.4.3 交易管理

#### （1）功能概述

交易管理用于支持居民之间的闲置物品撮合、下单、支付或线下交付确认、评价和纠纷处理，并明确平台的撮合与监管边界。

#### （2）业务需求

- 支持在线下单或约定线下交付；
- 支持物品锁定，避免重复成交；
- 支持买卖双方确认交付；
- 支持评价、举报和纠纷处理；
- 支持按平台规则收取服务费或不收费。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.4.3-01 | 交易撮合 | 支持买家发起购买、赠送领取、交换或租借申请 |
| FR-6.4.3-02 | 物品锁定 | 交易建立后锁定物品并阻止重复交易 |
| FR-6.4.3-03 | 订单与支付 | 收费交易调用公共订单与支付能力 |
| FR-6.4.3-04 | 交付确认 | 记录当面交付、验收和双方确认 |
| FR-6.4.3-05 | 取消与纠纷 | 处理取消、退款、举报和交易争议 |
| FR-6.4.3-06 | 双方评价 | 记录买卖双方评价和信用影响 |

#### （4）数据需求

核心数据对象包括闲置交易单、买方、卖方、物品引用、交易方式、订单引用、支付引用、交付记录、评价、举报和纠纷记录。

#### （5）业务规则

- 平台应明确撮合服务范围及责任边界；
- 交易取消、失败或退款后按规则恢复物品状态；
- 当面交付不得以系统确认代替必要的现场验货；
- 纠纷期间相关交易记录和证据不得删除；
- 涉及资金托管或个人结算的方案应在支付合规评审后确定。

## 6.5 技能分享与邻里服务

### 6.5.1 技能认证

#### （1）功能概述

技能认证用于将符合条件的居民登记为个人服务提供者，验证其身份、技能材料和服务风险等级，控制可发布的服务范围。

#### （2）业务需求

- 支持居民提交技能、经历和证明材料；
- 支持按服务类目配置认证要求；
- 支持低、中、高风险分级准入；
- 支持认证有效期、暂停和撤销；
- 支持专业服务引导至机构主体。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.5.1-01 | 申请登记 | 提交技能类别、说明、时间和服务范围 |
| FR-6.5.1-02 | 材料认证 | 提交并审核技能、资质或经验证明 |
| FR-6.5.1-03 | 风险分级 | 根据服务类别确定准入和审核要求 |
| FR-6.5.1-04 | 服务者建档 | 认证通过后建立个人服务提供者档案 |
| FR-6.5.1-05 | 状态管理 | 管理认证有效、暂停、到期和撤销状态 |

#### （4）数据需求

核心数据对象包括技能申请、申请人、技能类别、证明材料、风险等级、审核记录、认证状态、有效期和限制事项。

#### （5）业务规则

- 低风险服务可在实名认证后按规则发布；
- 中风险服务须补充技能证明或人工审核；
- 医疗、护理、儿童接送和长期托管等高风险服务不得由普通个人发布；
- 认证到期或撤销后相关服务自动下架；
- 认证结果不得替代法律法规要求的职业资质。

### 6.5.2 服务发布

#### （1）功能概述

居民技能服务发布用于认证居民将技能、可服务时间、区域和价格形成可检索、可预约的邻里服务，复用平台服务商品和时间库存能力。

#### （2）业务需求

- 支持固定服务和居民需求两类发布；
- 支持固定价格、参考价格或协商价格；
- 支持可服务时段、距离和社区范围；
- 支持内容审核和风险提示；
- 支持供需搜索和推荐。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.5.2-01 | 技能服务发布 | 配置服务说明、价格、时长和服务范围 |
| FR-6.5.2-02 | 需求发布 | 居民发布需要帮助的事项、时间和地点 |
| FR-6.5.2-03 | 时间配置 | 设置个人可服务日期、时段和接单上限 |
| FR-6.5.2-04 | 供需匹配 | 按类别、距离、时间和评价进行搜索或推荐 |
| FR-6.5.2-05 | 发布审核 | 对服务风险、内容和认证状态进行校验 |

#### （4）数据需求

核心数据对象包括技能服务、居民需求、服务规格、参考价格、时间库存、服务范围、匹配记录、发布状态和风险提示。

#### （5）业务规则

- 服务类别必须与有效认证范围一致；
- 平台限制事项不得通过自定义标题规避；
- 个人可服务量不得超过其时间库存；
- 推荐仅用于信息撮合，不替代用户选择；
- 价格、服务内容变化后历史预约保留原快照。

### 6.5.3 服务评价

#### （1）功能概述

服务评价用于在邻里服务完成后形成双方评价、信用记录、投诉和风险处置，为后续撮合和平台监管提供依据。

#### （2）业务需求

- 支持服务接受者评价服务提供者；
- 支持服务提供者评价交易配合情况；
- 支持标签、文字和投诉证据；
- 支持异常评价申诉；
- 支持评价结果影响展示和风控。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.5.3-01 | 双向评价 | 在服务完成后由双方提交星级、标签和文字评价 |
| FR-6.5.3-02 | 评价展示 | 按规则展示综合评分和近期评价 |
| FR-6.5.3-03 | 投诉举报 | 对服务质量、安全和违规行为发起投诉 |
| FR-6.5.3-04 | 申诉处理 | 支持被评价方提交证据并由平台复核 |
| FR-6.5.3-05 | 信用影响 | 将有效评价、投诉和处置结果计入信用档案 |

#### （4）数据需求

核心数据对象包括评价、评价标签、订单引用、评价对象、投诉、证据、申诉、处理结论和信用记录。

#### （5）业务规则

- 评价应基于真实完成或实际发生的业务；
- 双方评价在规则设定的时间后展示，减少报复性评价；
- 平台删除或屏蔽评价必须记录理由；
- 投诉结论与评价展示调整应分别留痕；
- 信用评分规则应可解释并允许纠错。

## 6.6 社区活动与社群运营

### 6.6.1 活动管理

#### （1）功能概述

活动管理用于策划、发布和管理老年、亲子、文化、健康、便民及商户联合活动，兼顾公益活动和收费活动。

#### （2）业务需求

- 支持活动、场次、主办方、合作方和场地；
- 支持人数、对象、年龄和材料等报名条件；
- 支持免费、付费和邀请制活动；
- 支持活动审核、发布、取消和变更；
- 支持与空间资源、合同和结算能力关联。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.6.1-01 | 活动策划 | 维护活动主题、内容、对象、主办方和合作方 |
| FR-6.6.1-02 | 场次管理 | 配置日期、时间、地点、容量和报名期限 |
| FR-6.6.1-03 | 报名规则 | 配置身份、年龄、人数、审核及材料要求 |
| FR-6.6.1-04 | 收费规则 | 配置免费、付费、优惠和退款规则 |
| FR-6.6.1-05 | 审核发布 | 支持活动审核、发布、变更、取消和通知 |
| FR-6.6.1-06 | 合作关联 | 关联场地、主办方合同和收益分配依据 |

#### （4）数据需求

核心数据对象包括活动、活动场次、主办方、合作方、活动场地、容量、报名规则、收费规则、发布版本和合同引用。

#### （5）业务规则

- 活动场次不得与已占用场地冲突；
- 涉及未成年人、旅游或高风险活动时须配置额外材料和责任要求；
- 活动重要变更应通知已报名人员；
- 取消付费活动应按规则触发退款；
- 活动版本变化不得修改已报名用户的交易快照。

### 6.6.2 报名管理

#### （1）功能概述

报名管理用于处理居民报名、审核、候补、支付、签到和退出。报名记录代表参与关系，交易订单仅在收费时产生。

#### （2）业务需求

- 支持本人及家庭成员报名；
- 支持一笔订单包含多人报名；
- 支持容量占用、候补和名额释放；
- 支持免费报名和付费报名；
- 支持签到、取消和退款联动。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.6.2-01 | 报名提交 | 选择场次、参与人并提交必要材料 |
| FR-6.6.2-02 | 资格与容量校验 | 校验报名条件、重复报名和剩余名额 |
| FR-6.6.2-03 | 审核与候补 | 支持自动确认、人工审核和候补排队 |
| FR-6.6.2-04 | 付费关联 | 付费活动调用订单、优惠和支付能力 |
| FR-6.6.2-05 | 取消与退款 | 取消报名、释放名额并按规则退款 |
| FR-6.6.2-06 | 签到核销 | 支持二维码、名单或人工签到 |

#### （4）数据需求

核心数据对象包括报名记录、参与人、监护人或联系人、场次、资格材料、审核状态、候补序号、订单引用、支付状态和签到记录。

#### （5）业务规则

- 免费活动可只有报名记录，不强制生成订单；
- 付费报名在支付完成后确认名额，特殊活动可先预占；
- 退款完成后应释放名额并按顺序通知候补人员；
- 一笔订单多参与人时应保持订单与报名记录一对多关系；
- 未成年人报名应记录监护人信息和必要授权。

### 6.6.3 社群运营

#### （1）功能概述

社群运营用于依据活动参与、居民兴趣和服务偏好形成主题社群，支撑活动触达、内容发布和居民持续参与。

#### （2）业务需求

- 支持创建老年、亲子、兴趣和志愿等主题社群；
- 支持从活动参与者沉淀成员；
- 支持成员申请、邀请、退出和移除；
- 支持社群公告、活动推荐和消息触达；
- 支持成员隐私和运营权限控制。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.6.3-01 | 社群创建 | 配置社群主题、介绍、规则和管理员 |
| FR-6.6.3-02 | 成员管理 | 支持申请、邀请、审核、退出和移除 |
| FR-6.6.3-03 | 活动关联 | 将活动参与者按授权加入或推荐至相关社群 |
| FR-6.6.3-04 | 内容与公告 | 发布社群公告、活动和服务推荐 |
| FR-6.6.3-05 | 运营统计 | 统计成员、活跃、活动参与和退出情况 |

#### （4）数据需求

核心数据对象包括社群、社群成员、管理员、加入方式、成员状态、公告、活动引用、消息记录和运营指标。

#### （5）业务规则

- 加入社群应取得用户同意，不得默认强制加入；
- 成员联系方式不应向普通成员直接暴露；
- 社群内容应符合平台内容管理规则；
- 管理员操作和成员移除应留痕；
- 社群标签不得直接推断敏感个人属性。

## 6.7 数据运营分析

### 6.7.1 运营统计

#### （1）功能概述

运营统计用于统一展示用户、主体、服务、资源、活动和交易等运营数据，为项目运营评估和课题验证提供量化依据。

#### （2）业务需求

- 支持按项目、社区、时间和业务类型统计；
- 支持统一指标字典和计算口径；
- 支持从汇总指标下钻到授权明细；
- 支持趋势、结构和异常对比；
- 支持导出课题研究所需脱敏数据。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.7.1-01 | 用户统计 | 统计认证、活跃、参与和复用用户 |
| FR-6.7.1-02 | 主体统计 | 统计入驻、活跃、暂停和退出主体 |
| FR-6.7.1-03 | 业务统计 | 统计服务、资源、闲置、技能和活动业务量 |
| FR-6.7.1-04 | 交易统计 | 统计订单、支付、退款、完成和评价情况 |
| FR-6.7.1-05 | 项目对比 | 按项目和场景比较运营指标 |
| FR-6.7.1-06 | 数据导出 | 按权限导出汇总或脱敏明细 |

#### （4）数据需求

核心数据对象包括指标定义、统计维度、事实数据、指标结果、统计周期、数据权限、导出任务和指标版本。

#### （5）业务规则

- 同一指标在不同看板和报表中应使用统一口径；
- 指标口径变更应保留版本和生效时间；
- 金额指标应区分订单金额、实付、退款和结算口径；
- 导出数据须遵守权限与脱敏要求；
- 研究数据应能够追溯至来源系统和统计规则。

### 6.7.2 服务分析

#### （1）功能概述

服务分析用于评估服务供给、预约、响应、履约、评价和异常情况，识别服务质量和运营改进方向。

#### （2）业务需求

- 支持按服务类别、主体、项目和时段分析；
- 支持预约转化、接单、完成和取消分析；
- 支持服务时效和评价分析；
- 支持异常订单、投诉和退款关联；
- 支持AI推荐采纳情况分析。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.7.2-01 | 供给分析 | 分析服务数量、覆盖范围、时间容量和主体分布 |
| FR-6.7.2-02 | 转化分析 | 分析浏览、咨询、预约、支付和完成转化 |
| FR-6.7.2-03 | 履约分析 | 分析接单率、准时率、完成率和平均耗时 |
| FR-6.7.2-04 | 质量分析 | 分析评分、投诉、退款和低评分原因 |
| FR-6.7.2-05 | 智能效果分析 | 分析派单建议、案例推荐的展示与采纳情况 |

#### （4）数据需求

核心数据对象包括服务供给指标、预约漏斗、履约时长、评价标签、投诉原因、退款原因、推荐记录和采纳结果。

#### （5）业务规则

- 完成率和响应时长应明确起止状态；
- 取消应区分用户、主体、平台和系统原因；
- 服务质量比较应考虑样本量；
- AI建议未展示、未采纳和采纳后效果应分别记录；
- 分析结果不应自动替代人工绩效或处罚结论。

### 6.7.3 社区治理分析

#### （1）功能概述

社区治理分析用于对居民诉求、社区事件、工单处置、巡检问题和风险预警进行统计，评估事件闭环和多主体协同效果。

#### （2）业务需求

- 支持事件来源、类型、空间和责任主体分析；
- 支持受理、派单、处理、回访和闭环时效分析；
- 支持重复问题和高发空间识别；
- 支持AI识别效果和人工修订情况分析；
- 支持风险提示跟踪。

#### （3）功能需求

| 编号 | 功能名称 | 功能说明 |
|---|---|---|
| FR-6.7.3-01 | 事件统计 | 统计事件来源、类型、位置和紧急程度 |
| FR-6.7.3-02 | 闭环分析 | 统计受理率、按时完成率、回访率和闭环率 |
| FR-6.7.3-03 | 协同分析 | 分析转派、协办、退回和跨组织流转情况 |
| FR-6.7.3-04 | 热点分析 | 识别高发问题、重复事件和重点空间 |
| FR-6.7.3-05 | AI效果分析 | 统计识别准确性、人工修订和建议采纳 |
| FR-6.7.3-06 | 风险跟踪 | 统计预警、确认、处置和关闭结果 |

#### （4）数据需求

核心数据对象包括事件事实、工单流转、时效、空间维度、责任组织、回访、AI识别记录、人工修订、预警和处置结果。

#### （5）业务规则

- 闭环率应以满足完结和必要回访条件为准；
- 重复事件合并不得减少真实事件数量统计；
- 责任主体分析应基于实际流转和处置记录；
- AI准确性应以人工确认或抽样标注为参照；
- 治理分析涉及个人信息时应汇总或脱敏展示。

# 7. 业务中台能力需求

业务中台位于业务应用与平台基础能力之间，只沉淀真正具有跨业务复用价值、独立生命周期或一致性要求的领域能力。本课题精简为五项核心业务中台，不再将统一身份、空间资源、活动、合同、营销权益、评价风控和数据分析分别建设为独立中台。

每项中台均采用模块化设计，可在同一Spring Boot应用中实现，不要求首期独立部署为微服务。

## 7.1 运营主体中台

**能力定位。** 统一管理能够经营、发布或履约的组织和个人主体，解决商户、服务机构和个人服务者在不同业务应用中重复建档、重复认证的问题。

**服务对象与调用场景。** 平台生态运营在主体入驻、商户管理和服务发布时调用；技能分享在个人服务者认证时调用；商品服务、订单、任务履约和计费结算能力据此识别经营主体、履约主体和结算对象。

**核心业务对象。** 运营主体、主体类型、认证申请、资质、服务区域、项目授权、主体人员关系、主体状态、收款及结算信息引用。

| 能力编号 | 能力名称 | 能力说明 |
|---|---|---|
| MC-7.1-01 | 主体统一建档 | 建立物业组织、商户、服务机构和个人服务者档案 |
| MC-7.1-02 | 入驻与认证 | 管理主体申请、材料审核、认证结果和有效期 |
| MC-7.1-03 | 资质与经营范围 | 管理服务资质、经营类目、服务区域和项目授权 |
| MC-7.1-04 | 主体人员关系 | 关联负责人、商户人员、服务人员及其有效状态 |
| MC-7.1-05 | 主体状态管理 | 管理正常、暂停、整改、退出和限制状态 |
| MC-7.1-06 | 结算信息引用 | 维护收款主体和结算对象所需的基础引用信息 |

**输入与输出。** 输入主体类型、基础资料、人员、资质和申请项目；输出主体编号、认证结果、有效资质、经营范围、主体状态和可用人员关系。

**业务边界与建设定位。** 账号认证、组织角色和权限属于平台基础能力；商品及服务内容属于商品与服务中台；支付和结算结果属于计费支付结算中台。本中台为**核心建设**。

## 7.2 商品与服务中台

**能力定位。** 建立商品与服务统一主数据，通过公共模型和业务扩展对象支撑社区便民服务、预约服务、居民闲置、技能服务以及可交易资源等不同供给形态。

**服务对象与调用场景。** 平台生态运营、闲置交易、技能分享和收费活动在发布、审核、展示、预约和下单前调用；交易订单中台据此生成交易快照；任务履约中台据此获取服务要求。

**核心业务对象。** 类目、商品、服务、SKU、服务规格、价格、普通库存、时间库存、服务区域、服务时间、发布主体、上下架状态和业务扩展对象。

| 能力编号 | 能力名称 | 能力说明 |
|---|---|---|
| MC-7.2-01 | 统一类目与主数据 | 管理商品、服务、闲置和技能服务的分类及公共信息 |
| MC-7.2-02 | SKU与服务规格 | 表达实物规格、服务时长、套餐、人数和预约容量 |
| MC-7.2-03 | 价格与可售条件 | 管理价格、区域、时间、对象和项目范围 |
| MC-7.2-04 | 库存与时间库存 | 管理普通数量库存及预约时段容量 |
| MC-7.2-05 | 审核与上下架 | 管理发布审核、上架、下架、暂停和失效 |
| MC-7.2-06 | 场景扩展 | 通过业务类型、扩展对象或扩展表承载特有信息 |
| MC-7.2-07 | 交易快照提供 | 向订单中台提供下单时不可变的供给、价格和履约信息 |

**输入与输出。** 输入主体、类目、规格、价格、区域、时间和场景特有信息；输出商品或服务编号、可售状态、有效规格、价格、库存及预约条件。

**业务边界与建设定位。** 订单及支付状态不在本中台管理；空间可用时段由空间资源运营业务校验；实际任务过程归任务履约中台。本中台为**核心建设**，复杂促销价、仓储和供应链能力不纳入课题首期。

## 7.3 交易订单中台

**能力定位。** 统一管理不同业务交易的公共订单主数据、订单项、交易快照、金额和公共状态，为支付、履约、取消、退款和统一查询提供稳定交易依据。

**服务对象与调用场景。** 服务预约、空间预约、闲置交易、技能服务和付费活动在产生交易时调用；计费支付结算、任务履约及数据分析能力通过平台订单编号关联交易结果。

**核心业务对象。** 平台订单、订单项、金额明细、交易快照、业务关联、公共订单状态、支付状态、履约状态、取消记录和退款申请。

| 能力编号 | 能力名称 | 能力说明 |
|---|---|---|
| MC-7.3-01 | 统一订单创建 | 按业务类型、业务单据和交易双方创建平台订单 |
| MC-7.3-02 | 订单项与交易快照 | 保存下单时的供给、价格、主体及履约方式快照 |
| MC-7.3-03 | 公共状态管理 | 管理待支付、进行中、完成、取消和关闭等公共状态 |
| MC-7.3-04 | 支付与履约状态映射 | 汇总支付和履约结果，不代替对应模块详细状态 |
| MC-7.3-05 | 取消与退款申请 | 执行公共校验并发起退款处理 |
| MC-7.3-06 | 统一查询与审计 | 按用户、主体、项目、类型和状态查询订单及轨迹 |

**输入与输出。** 输入业务类型、业务单据ID、交易双方、订单项、金额和扩展引用；输出平台订单ID、订单编号、公共状态以及后续支付和任务关联信息。

**公共订单与业务单据边界。**

- 中台统一平台订单编号、交易双方、订单项、金额、支付状态、履约状态和公共主状态；
- 服务预约单、空间预约单、活动报名记录、闲置交易单和技能服务预约单由业务应用保存特有字段和特有流程；
- 业务应用通过平台订单ID、业务类型、业务单据ID、业务子状态和扩展对象与公共订单关联；
- 公共主状态与业务子状态通过明确映射规则同步；
- 各业务可以拥有自己的详情页面和特有操作。

**业务边界与建设定位。** 中台不负责空间冲突、服务排班、活动名额等场景规则，也不建设跨商户复杂购物车、智能拆合单和完整电商售后体系。本中台为**核心建设**。

## 7.4 任务履约中台

**能力定位。** 将物业事件、工单、服务预约和其他业务需求转化为可分派、可执行、可跟踪和可回传的任务，统一派单、接单、转派、到场、处理、SLA及异常管理。

**服务对象与调用场景。** 物业服务在报修、投诉、巡检问题和设备维修时调用；社区服务与技能服务在人员分配、上门服务和结果确认时调用；交易订单中台接收履约状态回传。

**核心业务对象。** 任务、任务类型、来源业务、执行组织、班组、人员、技能、服务区域、排班、派单记录、处理过程、SLA、异常和完成结果。

| 能力编号 | 能力名称 | 能力说明 |
|---|---|---|
| MC-7.4-01 | 任务统一生成 | 根据事件、工单、订单或业务单据生成标准任务 |
| MC-7.4-02 | 候选人与排班 | 根据区域、技能、班组、排班和可用状态形成候选 |
| MC-7.4-03 | 派单与接单 | 支持人工、规则和AI辅助派单，以及接单、退单和转派 |
| MC-7.4-04 | 协同与过程 | 支持协办、到场、处理说明、附件、材料和核销 |
| MC-7.4-05 | SLA与异常 | 管理响应时限、处理时限、挂起、超时和升级 |
| MC-7.4-06 | 完成与状态回传 | 保存完成结果并向来源业务和订单回传状态 |
| MC-7.4-07 | 智能协同反馈 | 记录AI候选、人工选择、修改原因及最终处置效果 |

**输入与输出。** 输入来源业务、位置、时间、任务类型、技能、主体和服务要求；输出任务编号、候选人员、派单结果、过程轨迹、异常和完成结果。

**与流程、规则和AI的边界。**

- 任务履约中台负责任务如何生成、分派、执行和闭环；
- 流程引擎负责节点、条件、退回和办理路径；
- 规则引擎负责候选筛选、时限和自动动作；
- AI负责候选推荐、相似案例和建议，不直接确定责任人；
- 物业工单和商业服务订单保留各自业务单据，共用任务及调度接口。

**业务边界与建设定位。** 既有物业工单能力优先复用；跨场景任务接口、统一过程模型及智能协同反馈为**核心建设**。

## 7.5 计费支付结算中台

**能力定位。** 统一承接计费、应收、支付、退款、核销、对账和基础结算能力，避免各收费业务分别建设金额、支付和结算记录。

**服务对象与调用场景。** 物业收费、收费服务、空间预约、闲置交易、技能服务和付费活动在计价、收款、退款及基础结算时调用。

**核心业务对象。** 收费项目、计费规则、应收账单、账单明细、支付单、退款单、核销记录、支付渠道流水、收款主体、结算对象、对账记录和结算记录。

| 能力编号 | 能力名称 | 能力说明 |
|---|---|---|
| MC-7.5-01 | 收费项目与计费规则 | 管理收费对象、计费方式、价格来源和生效范围 |
| MC-7.5-02 | 应收账单 | 根据业务依据生成应收账单和明细 |
| MC-7.5-03 | 支付受理 | 根据订单或账单创建支付单并隔离支付渠道 |
| MC-7.5-04 | 支付确认与核销 | 幂等接收支付结果，完成账单或订单核销 |
| MC-7.5-05 | 退款处理 | 根据业务审核结果创建退款单并跟踪渠道状态 |
| MC-7.5-06 | 对账基础 | 核对业务订单、平台支付单和渠道流水 |
| MC-7.5-07 | 基础结算 | 按结算对象、周期和简单规则形成结算明细与记录 |

**输入与输出。** 输入收费依据、订单或业务单据、金额、收款主体、支付渠道和结算对象；输出账单、支付单号、支付状态、退款结果、核销记录、对账结果和基础结算记录。

**业务边界与建设定位。**

- 订单中台负责交易主状态，本中台负责金额形成、资金状态和结算记录；
- 外部支付机构负责实际资金处理；
- 业务应用负责是否允许收费、取消或退款的业务判断；
- 首期不建设金融级账户体系、复杂多级分账、财务总账、跨机构清算和自动开票平台；
- 复杂物业计费可优先复用现有系统，本课题重点建设统一接口、支付退款和基础结算闭环。

本中台为**基础版本建设与现有能力复用相结合**。

| 技能分享与邻里服务 | 个人服务者认证、服务发布、预约和履约 | 运营主体、商品与服务、交易订单、任务履约、计费支付结算 | 统一身份、规则、评价与风险分析 | 个人主体、技能服务、任务和交易结果 |
| 社区活动与社群运营 | 活动发布、报名、收费、签到 | 交易订单、计费支付结算 | 空间基础模型、活动业务模块、消息和数据分析 | 报名记录、订单、支付、签到和参与统计 |

## 7.7 典型调用链

**商户入驻与商品/服务发布：** 商户提交入驻 → 运营主体中台完成主体建档和认证 → 平台基础能力创建或关联账号、组织及权限 → 商户在授权经营范围内发布商品或服务 → 商品与服务中台建立商品/服务主数据 → 返回主体编号、认证状态及商品/服务编号。

**居民商城购物：** 居民浏览商品 → 商品与服务中台返回商品、SKU、价格和库存 → 居民确认商品及履约方式 → 交易订单中台生成公共订单和交易快照 → 积分能力计算可用抵扣 → 计费支付结算中台完成支付 → 商品库存扣减 → 商户按配送、自提或到店核销方式履约 → 订单完成后按规则发放积分并支持评价。

**社区团购：** 平台或商户创建团购活动 → 商品与服务中台提供商品/服务及可售条件 → 团购应用配置团购价、活动时间和成团规则 → 居民开团或参团 → 交易订单中台生成订单 → 计费支付结算中台完成支付 → 达到条件后确认成团并进入配送、自提、核销或服务履约 → 未成团则关闭活动并按规则退款 → 团购完成后发放积分并记录评价。

**居民预约社区服务：** 居民选择服务和服务对象 → 商品与服务中台返回服务、价格和可预约条件 → 业务应用创建服务预约单 → 交易订单中台生成公共订单 → 积分能力计算可用抵扣 → 计费支付结算中台完成计费、支付和核销 → 任务履约中台分配服务人员并记录过程 → 履约结果回传业务应用和订单 → 完成后按规则发放服务积分和评价积分 → 数据运营与研究验证中心汇总运营及课题指标。

**空间资源预约：** 居民选择空间资源 → 空间与资源运营应用调用空间基础模型获取资源关系 → 业务规则校验时段、容量和资格 → 收费场景调用交易订单中台和计费支付结算中台 → 业务应用记录签到、使用和释放 → 按规则发放参与积分 → 数据运营与研究验证中心统计资源利用情况。

**闲置交易：** 居民发布闲置物品 → 商品与服务中台建立闲置供给 → 业务应用完成内容审核 → 交易达成后交易订单中台创建订单 → 收费场景调用计费支付结算中台 → 双方确认交付并记录评价 → 风险分析能力汇总投诉和异常。

**技能分享与邻里服务：** 居民提交技能认证 → 运营主体中台建立个人服务主体 → 商品与服务中台发布技能服务 → 居民预约后调用交易订单、计费支付结算和任务履约中台 → 服务完成后保存评价和履约结果。

**社区活动：** 运营人员通过活动业务模块发布活动和场次 → 业务应用管理报名资格、名额和签到 → 免费活动仅形成报名记录 → 付费活动调用交易订单和计费支付结算中台 → 活动签到后按规则发放积分 → 数据运营与研究验证中心统计参与情况。

## 7.8 业务中台与创新点一的关系

模型驱动与低代码动态装配应将五项核心中台能力作为可治理的装配单元，支持中台能力注册、输入输出Schema定义、场景模板绑定、调用参数配置、返回结果映射、业务单据关联、业务扩展对象配置以及调用版本、权限和审计控制。

动态装配只能调用已注册、已授权且通过版本校验的中台能力，不允许通过配置直接修改中台数据表或绕过金额、状态和权限校验。

## 7.9 业务中台与创新点二的关系

AI语义识别和知识图谱通过平台基础能力获取用户身份、房屋和空间关系，通过运营主体及商品服务中台识别责任主体和服务类型，通过任务履约中台形成处置任务并记录人工选择，通过交易订单及计费支付结算中台获取受控交易上下文，通过数据运营与研究验证中心统计识别、推荐和知识应用效果。

AI输出必须经过业务规则、中台服务和人工确认后进入正式业务流程，不得形成与业务脱节的聊天或问答模块。

# 8. 创新点二需求：AI语义识别与运维知识图谱

## 8.1 建设目标

建设面向社区实际业务的AI智能协同能力，使文本、语音、图片说明、历史工单、巡检和设备数据能够转化为结构化事件和可复用知识。AI能力以辅助识别、辅助推荐和风险提示为主，不替代有权人员的业务决定。

## 8.2 输入与数据来源

AI能力应支持以下输入：

- 居民提交的报修、投诉、建议、咨询和求助文本；
- 居民语音及其转写文本；
- 物业客服或社区工作人员代录内容；
- 工单描述、处理过程和回访评价；
- 巡检问题、设备告警和维修记录；
- 经授权的图片、附件和结构化业务字段；
- 已审核的维修知识、服务规范和风险规则。

原始输入、模型输出、人工修订和最终业务结果应分别保存，便于审计和效果评估。

## 8.3 AI诉求识别

### 8.3.1 文本与语音预处理

系统应支持语音转写、文本清洗、口语化表达归一、噪声信息过滤和上下文拼接。语音转写失败或质量低时，应允许重新录入或转人工处理。

### 8.3.2 意图识别

系统应识别报修、投诉、咨询、建议、求助、服务预约、活动咨询等主要意图，并允许一个输入包含主意图和附加意图。意图分类体系应可配置和版本化。

### 8.3.3 实体提取

系统应从诉求中提取项目、社区、楼栋、房屋、公共区域、设备、故障类型、事件地点、发生时间、紧急程度、联系人和服务需求等实体。实体应与平台主数据匹配，匹配不确定时给出候选项。

### 8.3.4 置信度与人工校验

每项识别结果应返回置信度或等价质量标识。低置信度、关键字段缺失、存在冲突或涉及安全风险的事件必须转人工校验。人工修订应作为后续样本优化依据。

## 8.4 自动事件结构化

系统应根据识别结果生成事件草稿，至少包含原始诉求、事件类型、关联空间、关联对象、紧急程度、建议责任主体和必要补充问题。事件草稿经人工确认后，可创建正式事件或工单。

系统应支持以下处理：

1. 对缺失的关键字段向居民或工作人员发起补充询问；
2. 对可能重复的事件给出关联建议；
3. 对不属于平台处理范围的事项提示转人工或其他渠道；
4. 保持原始输入与结构化结果的可追溯关系；
5. 防止大模型生成不存在的房屋、设备、人员或处理结果。

## 8.5 智能派单辅助

系统应综合事件类型、空间位置、责任区域、人员技能、值班状态、当前工作量、历史处理效果和紧急程度生成派单建议。建议应列出候选责任组织或人员及主要依据。

智能派单仅提供建议，不应绕过组织权限、值班规则和人工确认。派单结果、是否采纳、修改原因和最终处置效果应记录，用于评估推荐有效性。

## 8.6 运维知识图谱

### 8.6.1 知识对象

知识图谱至少应覆盖项目、空间、房屋、设备、故障、事件、工单、人员、组织、技能、服务、维修方案、材料和风险事件等对象。

### 8.6.2 知识关系

系统应支持表达“设备位于空间”“设备发生故障”“事件关联设备”“工单处理事件”“人员具备技能”“人员所属组织”“故障采用维修方案”“方案使用材料”“风险关联设备或空间”等关系。

### 8.6.3 知识抽取与审核

系统可从结构化业务数据和文本记录中抽取候选知识。自动抽取的知识应标识来源、时间、可信度和审核状态；影响推荐或风险判断的重要知识必须经人工审核后生效。

### 8.6.4 知识更新与失效

知识应支持新增、修订、合并、失效和版本记录。设备迁移、人员离岗、维修方案变更等业务变化应同步更新关联知识，历史关系不得被无痕覆盖。

## 8.7 相似案例与维修建议

系统应根据事件文本、故障类型、设备类别、空间位置和知识关系检索相似历史案例，展示相似度、历史处置方案、处理人员、耗时和结果。维修建议应来源于已审核知识、业务规则和相似案例，不得生成未经验证的安全操作。

涉及电气、消防、燃气、电梯等高风险设备时，系统只提供经批准的处置规范和升级提示，不提供替代专业判断的操作指令。

## 8.8 风险提示

系统应根据重复故障、同一空间高频事件、设备异常、超时工单和历史风险关系生成风险提示。每条提示应包含触发依据、关联对象、建议检查项、风险级别和有效期。

风险提示应由责任人员确认、处置或驳回，并记录理由。未经确认的AI提示不得直接形成处罚、停用或对外结论。

## 8.9 人机协同与安全要求

- AI输出必须标识为机器建议；
- 原始诉求、模型版本、提示模板、输出和人工修改应可追溯；
- 敏感信息进入外部模型前应按安全方案脱敏或取得授权；
- 模型不可用、超时或输出异常时应降级为人工受理；
- 知识库和模型服务应按项目、组织和数据等级控制访问；
- 不得使用居民数据进行与课题无关的训练或画像；
- 涉及人身安全、资金、处罚和责任认定的结果必须人工确认。

## 8.10 效果验证指标

本阶段先确定指标口径，具体目标值由样本规模、基线测试和开题或设计评审确认。

| 指标 | 口径说明 |
|---|---|
| 意图识别准确率 | 经人工标注的测试样本中，主意图识别正确的比例 |
| 关键实体提取准确率 | 位置、对象、故障、时间等关键实体识别的准确性 |
| 工单草稿可用率 | AI生成草稿经少量修订即可使用的比例 |
| 人工修订率 | 结构化结果中需要人工修改的记录比例 |
| 派单建议采纳率 | 建议被直接或主要采纳的比例 |
| 相似案例有效率 | 使用人员认为推荐对处置有帮助的比例 |
| 知识覆盖率 | 已审核知识覆盖目标设备、故障和方案的程度 |
| 平均流转时间变化 | 使用AI辅助前后诉求受理至派单的时间变化 |
| 风险提示闭环率 | 已确认风险提示完成处置并关闭的比例 |

# 9. 创新点一需求：模型驱动与低代码动态装配

## 9.1 建设目标

建设面向多业态项目的模型驱动与低代码装配能力，将不同项目反复开发的空间结构、组织关系、业务对象、表单、流程、规则和权限转化为可复用模型与配置，实现“标准模板+项目参数+差异化配置+必要扩展”的交付方式。

## 9.2 模型体系

### 9.2.1 空间模型

空间模型应支持社区—小区—楼栋—单元—房屋、楼宇—楼层—房间、公寓—楼栋—房间等不同层级，允许项目配置节点类型、层级约束和可挂载业务对象。空间模型变化应通过版本管理和迁移规则保障历史业务。

### 9.2.2 组织模型

组织模型应描述平台运营方、物业、社区、商户、服务机构和内部班组等组织，并建立组织与项目、空间、角色、人员和数据范围的关系。不同业态可替换组织类型，但权限与协同机制复用。

### 9.2.3 服务模型

服务模型应统一描述服务类目、服务项目、规格、价格方式、服务范围、时间库存、履约方式和风险等级。大光路的便民服务、办公楼的企业服务和公寓的租住服务可使用相同模型并配置不同目录。

### 9.2.4 业务对象模型

业务对象模型应支持定义实体、字段、关联、状态、校验和展示属性，用于描述居民诉求、服务预约、空间预约、活动报名等业务单据。核心交易、支付和权限对象保持标准化，不允许任意配置破坏数据一致性。

### 9.2.5 模型关系

系统应支持“人—空间—角色”“组织—项目—权限”“服务—主体—范围”“事件—空间—对象”“业务单据—交易订单—履约任务”等关系，并提供关系完整性校验。

## 9.3 元数据管理

元数据应覆盖实体、字段、表单、流程、规则、权限、组件和接口映射。系统应支持元数据创建、校验、发布、版本、依赖分析和停用。

元数据修改应区分：

- 可直接生效的展示类配置；
- 需要数据迁移的模型变更；
- 需要流程兼容的状态变更；
- 不允许在线修改的核心交易与安全规则。

## 9.4 动态表单配置

系统应支持字段类型、布局、必填、默认值、校验、联动、可见性和附件要求配置。动态表单应能够绑定业务对象模型，并根据角色、状态和场景展示不同字段。

报修表单可配置图片和位置，保洁服务可配置面积和时间，活动报名可配置参与人和监护信息。关键业务字段应结构化存储，不应全部放入不可查询的JSON。

## 9.5 流程配置

系统应支持对审核、事件流转、服务受理和资源预约等流程进行配置，包括节点、角色、条件、时限、退回、转办和通知。流程实例启动后应绑定流程版本，后续配置变更不得无规则影响运行中的实例。

支付、退款、订单金额和权限校验等高安全逻辑不应完全交由可视化流程自由编排。

## 9.6 规则配置

系统应支持服务可售范围、预约资格、资源收费、活动报名、派单、超时、风险分类和消息触达等规则配置。规则应具备优先级、适用范围、生效时间、测试、发布和回滚能力。

规则结果应可解释，至少能够说明命中的规则、输入条件和输出结果。冲突规则应在发布前被识别或按明确优先级处理。

## 9.7 场景模板管理

场景模板应封装一类场景所需的模型、表单、流程、规则、权限和基础字典。系统应支持模板创建、复制、继承、差异对比、版本发布和项目实例化。

建议首批形成：

1. 居民报修与工单模板；
2. 服务预约模板；
3. 空间资源预约模板；
4. 社区活动报名模板；
5. 办公楼或公寓模拟验证模板。

## 9.8 动态装配与能力调用

业务应用应通过配置组合业务中台能力，而不是复制其代码。例如服务预约模块在居民提交预约时：

1. 使用服务模型校验服务、范围和时段；
2. 创建服务预约业务单据；
3. 调用交易订单能力创建收费订单；
4. 调用支付能力完成付款；
5. 支付成功后创建履约任务；
6. 履约完成后更新交易订单；
7. 通过事件触发评价、统计或其他后续动作。

配置中心应记录业务动作与中台能力之间的映射，但核心接口入参、金额校验和状态一致性仍由代码保障。

## 9.9 多项目复制能力

系统应支持将标准模板实例化到新项目，并完成项目参数、空间结构、组织角色、服务目录、表单、流程和规则配置。项目差异应以覆盖配置或扩展模块承载，避免直接复制整套代码。

复制过程应提供依赖检查、配置预览、冲突提示、发布验证和失败回滚。项目数据应保持隔离，模板升级不得未经确认覆盖项目差异配置。

## 9.10 配置发布、版本与回滚

所有影响运行的配置应经过草稿、校验、测试、审批和发布流程。系统应支持：

- 配置版本号及变更说明；
- 发布前依赖和冲突检查；
- 测试环境或预览实例验证；
- 指定时间生效；
- 运行版本与历史版本查询；
- 失败回滚和紧急停用；
- 发布操作审计。

## 9.11 扩展边界

以下内容适合配置：字段、表单布局、审批节点、服务范围、时效、展示规则、场景参数和消息模板。

以下内容原则上通过标准代码实现：身份认证、权限校验、订单金额、支付回调、退款核验、数据隔离、审计、幂等和事务一致性。

场景特有且稳定的复杂逻辑可通过独立业务模块扩展，并通过标准接口调用公共能力，不应强行转化为难以维护的通用配置。

## 9.12 效果验证指标

| 指标 | 口径说明 |
|---|---|
| 场景配置完成时间 | 从模板选择到可执行场景发布所需时间 |
| 配置覆盖率 | 目标需求中可通过配置完成的需求比例 |
| 公共能力复用率 | 场景使用标准身份、订单、流程等能力的程度 |
| 模板直接复用比例 | 未修改或仅参数化后即可使用的模板项比例 |
| 差异化配置比例 | 项目差异通过配置而非代码实现的比例 |
| 配置发布成功率 | 通过校验并成功发布的配置版本比例 |
| 回滚有效性 | 发布异常后能恢复至前一稳定版本的验证结果 |
| 跨业态适配结果 | 社区模板在办公楼或公寓模拟项目中的复用情况 |

# 10. 数据需求

## 10.1 数据范围

系统数据分为基础主数据、业务过程数据、交易与履约数据、AI与知识数据、配置元数据和研究验证数据。

| 数据类别 | 主要内容 |
|---|---|
| 基础主数据 | 项目、空间、房屋、用户、组织、商户、服务机构、设备 |
| 业务过程数据 | 居民诉求、工单、服务预约、资源预约、闲置交易、技能服务、活动报名 |
| 交易与履约数据 | 订单、订单项、价格快照、支付状态、退款、履约任务、核销和评价 |
| AI与知识数据 | 原始诉求、转写文本、标注、识别结果、人工修订、知识实体、关系和来源 |
| 配置元数据 | 模型、字段、表单、流程、规则、权限、模板、版本和发布记录 |
| 验证数据 | 指标定义、样本集、测试结果、采纳记录、时间指标和用户反馈 |

## 10.2 统一数据关系

系统应建立以下核心关系：

- 用户与账号、家庭、房屋、项目和角色的关系；
- 空间与房屋、资源、设备、事件和组织的关系；
- 运营主体与门店、人员、资质、服务和项目的关系；
- 业务单据与交易订单、支付、履约、评价的关系；
- 事件与工单、设备、故障、人员和维修方案的关系；
- 场景模板与模型、表单、流程、规则和项目实例的关系。

## 10.3 业务单据与公共订单

服务预约、空间预约、活动报名、闲置交易和技能服务等场景应建立独立业务单据，保存场景特有信息；收费业务可关联统一交易订单，保存买卖双方、订单项、金额、支付和售后等公共信息。

免费活动、免费预约或仅记录服务过程的事项可以不产生交易订单。系统不得为了统一而强制所有业务生成无意义订单，也不得让各业务模块分别建设重复的支付和退款数据。

## 10.4 数据质量

系统应支持必填、格式、唯一性、引用完整性、状态一致性和跨对象关系校验。主数据合并、空间变更、身份变更和知识修订应保留来源与历史。

AI生成的数据必须标识模型来源和审核状态；未经审核的候选知识不得与正式知识混用。

## 10.5 数据权限与隐私

- 按项目、组织、角色、空间和数据对象实施访问控制；
- 个人信息只采集实现业务所需的最小范围；
- 敏感信息在展示、导出、日志和AI调用中按规则脱敏；
- 用户授权、撤回和代办关系应有记录；
- 研究使用的数据原则上脱敏或匿名化；
- 数据导出和批量查询应记录操作人、用途和结果。

## 10.6 数据生命周期

系统应根据数据类别配置保存、归档、失效和删除策略。订单、支付、合同、工单、审核和审计等记录的保存周期应符合适用法规及企业制度。数据删除应处理关联关系，不得导致历史业务无法解释。

# 11. 接口需求

## 11.1 现有物业系统接口

系统应根据现有物业系统能力，复用或同步项目、空间、房屋、居民身份、物业人员、收费、报修、工单、停车和公告等数据。接口应明确主数据来源、同步方向、更新频率、冲突处理和失败补偿。

原则上优先通过标准接口或扩展层集成，避免直接修改既有系统核心数据表。

## 11.2 用户端与管理端接口

居民端、商户或服务主体端、物业端和运营管理端应通过统一身份认证和标准业务接口访问系统。接口应按用户身份和项目范围进行授权，不得依赖前端隐藏实现权限控制。

## 11.3 AI服务接口

AI服务接口应支持语音转写、文本理解、结构化输出、语义检索和知识查询。结构化输出应使用约定的数据结构并进行字段校验。接口应记录模型、版本、耗时、输入摘要、输出、置信度和异常信息。

## 11.4 支付与消息接口

如验证场景涉及真实收费，系统应通过合规支付渠道完成下单、支付回调和退款，并具备签名校验、幂等和对账能力。消息接口应支持小程序或公众号消息、短信及站内消息中的一种或多种，并按用户授权和业务重要程度触达。

## 11.5 文件与媒体接口

系统应支持图片、语音和业务附件上传、访问控制、病毒或文件类型校验、存储和生命周期管理。文件访问地址不应绕过业务权限长期公开。

## 11.6 接口通用要求

- 采用统一身份认证、接口签名或令牌机制；
- 明确接口版本、请求标识和幂等要求；
- 对超时、重复、乱序和失败提供重试或补偿；
- 关键接口调用应记录审计日志；
- 外部系统不可用时应提供降级或人工处理路径；
- 接口详细参数在概要设计或接口设计阶段确定。

# 12. 非功能需求（简版）

## 12.1 性能要求

系统应满足大光路社区日常物业、运营和管理使用需求，并为后续多项目扩展预留容量。普通查询、提交和管理操作应保持可接受的交互响应；AI识别、报表和批量任务可采用异步处理，并向用户展示处理状态。

具体并发量、响应时间、数据容量和AI超时阈值应在完成用户规模、业务量和部署资源评估后确定，并形成性能测试基线。

## 12.2 安全要求

系统应具备身份认证、最小权限、数据隔离、传输加密、敏感数据保护、接口防护、文件安全、操作审计、备份恢复和AI调用安全能力。支付、退款、权限变更、配置发布、数据导出和人工修订AI结果等关键操作应重点审计。

## 12.3 可扩展要求

系统应采用模块化、接口化设计，支持新增项目、空间类型、主体类型、服务类目、业务单据、场景模板和AI能力。公共能力与场景特有逻辑应解耦，避免在统一订单、身份和权限模块中写入大光路专属规则。

## 12.4 可维护要求

系统应提供统一日志、异常定位、配置版本、接口监控、任务补偿、字典管理和运行文档。业务状态变化应通过明确的操作或状态机执行，不得依赖直接修改数据库。关键规则和指标口径应可查询、可解释和可追溯。

# 13. 研究验证方案

## 13.1 验证原则

研究验证应以真实或脱敏后的大光路业务数据、受控测试样本和可复现场景为基础，建立“需求—能力—场景—指标—证据”对应关系。没有实际样本或业务基础的指标不预设不合理的高目标值。

## 13.2 模型驱动与低代码验证

选择居民报修、服务预约、空间预约和活动报名中的不少于三个代表性场景，完成：

1. 建立或复用空间、组织、服务和业务对象模型；
2. 配置动态表单、流程、规则和权限；
3. 从场景模板创建大光路项目实例；
4. 将一个通用场景复制至办公楼或公寓模拟项目；
5. 记录配置时间、代码扩展点、复用项和差异项；
6. 验证配置发布、版本对比和回滚。

验证证据包括配置版本、发布记录、测试用例、运行截图或日志、差异清单和复用分析报告。

## 13.3 AI能力验证

建立经人工标注的社区诉求样本集，覆盖报修、投诉、咨询等意图以及空间、设备、故障和时间等关键实体。分别验证语音转写后的识别和直接文本识别。

在受控工单或真实业务试点中记录：

- AI识别结果与人工确认结果；
- 工单草稿人工修订内容；
- 派单建议及是否采纳；
- 相似案例是否被使用；
- 风险提示的确认和闭环；
- 模型异常和人工兜底情况。

训练样本、测试样本和最终评估样本应合理区分，避免使用同一数据重复证明效果。

## 13.4 知识图谱验证

选取设备故障或高频物业问题，建立设备、故障、空间、工单、人员和维修方案关系。验证知识来源、审核、更新、失效、相似案例查询和关系追溯。

重点检查推荐结果是否能够追溯到已审核知识或历史案例，以及设备迁移、人员变更和方案失效后知识是否正确更新。

## 13.5 场景应用验证

| 验证场景 | 主要验证内容 |
|---|---|
| 居民报修与工单 | 多渠道输入、AI结构化、流程配置、派单辅助、闭环分析 |
| 服务预约 | 服务模型、业务单据、订单调用、时间库存、履约协同 |
| 空间预约 | 空间模型、预约规则、冲突校验、核销和利用率 |
| 活动报名 | 活动场次、免费与付费分流、报名与订单关系、签到 |
| 多业态复制 | 模板继承、空间和身份替换、差异配置及代码复用 |

## 13.6 验收成果对应

系统需求与课题预期成果的对应关系如下：

| 课题成果 | 系统支撑 |

| 软件著作权2项 | 可围绕平台化配置能力和AI智能协同能力形成软件成果 |

| 综合研究报告1篇 | 研究过程、技术路线、指标结果、场景验证和推广结论 |

# 14. 风险与约束

## 14.1 业务范围风险

运营设想可能持续扩展，导致课题被要求实现完整商城、复杂结算或全部社区服务。应以本需求基线和阶段评审控制范围，新增重大业务方向须经过需求变更。

## 14.2 现有系统集成风险

既有物业系统的数据模型、接口和代码质量可能限制复用。应先开展接口和主数据评估，明确系统边界；确需扩展时采用独立模块或适配层，并保留升级路径。

## 14.3 模型与配置复杂度风险

过度追求通用可能使模型、流程和规则难以理解。应以典型场景驱动抽象，设置配置边界，对安全和稳定性要求高的逻辑坚持代码实现。

## 14.4 数据质量与样本风险

空间、设备、工单和居民数据可能存在缺失或不一致，AI样本量也可能不足。应先建立数据字典和质量规则，以“规则+人工标注+逐步积累”方式建设AI与知识能力。

## 14.5 AI效果与可靠性风险

居民口语、方言、噪声和复杂上下文可能降低识别效果，大模型也可能产生不实内容。应采用结构化约束、置信度、主数据校验、人工确认、模型降级和全过程留痕。

## 14.6 知识图谱有效性风险

项目初期知识稀疏，自动抽取结果可能不稳定。应优先建设高频故障和核心设备的小范围知识图谱，重要知识经审核后使用，并以业务效果而非图谱规模作为评价依据。

## 14.7 跨业态复制风险

社区、办公楼和公寓在空间、用户和服务方面存在差异。应复制通用模型和能力，不承诺业务页面及全部规则零修改；通过差异清单评估真实复用程度。

## 14.8 合规与安全风险

居民个人信息、语音、图片、支付和个人服务撮合涉及合规风险。应在上线前完成隐私、支付、内容审核和高风险服务边界评审，并取得必要授权。

## 14.9 项目约束

- 课题周期为2026年6月至2027年12月；
- 2026年重点完成总体方案、平台基础能力和模型驱动初步验证；
- 2027年重点完成AI、知识图谱、系统集成和大光路场景验证；
- 研究成果须支持平台、软件著作权、论文和综合研究报告；
- 需求变更应遵循课题和项目管理程序。

1. 现有物业系统可复用模块、接口范围和数据主责；
2. 大光路首批实际验证的服务、空间和活动场景；
3. 是否启用真实支付，以及支付、退款、结算的责任主体；
4. 商户、服务机构和个人服务提供者的准入与审核责任；
5. 居民身份认证、家庭代办和适老化服务的授权方式；
6. AI模型部署方式、语音识别服务和数据出域边界；
7. 训练、测试和验收样本规模及标注方法；
8. 意图识别、实体提取、派单建议等指标目标值；
9. 知识图谱首批设备、故障和维修知识范围；
10. 多业态复制验证选择办公楼还是公寓及其模拟数据来源；
