# 大光路物业运营平台｜总体需求与范围说明

> 版本：V0.1 · 2026-11-04  
> 当前工作：INIT 项目初始化与项目级文档准备。  
> 文档状态：总体范围建议稿；不表示所有业务规则、阶段划分或日期已经确认。  
> 本轮不启动 Stage00 业务详细设计、页面设计或原型实现。

## 1. 目标与文档职责

平台面向居民、商户及服务机构、社区和物业工作人员，统筹基础档案、物业服务、社区治理、安全监管和便民运营。目标是让同一事项在相应角色之间有清晰的责任、办理过程和结果，并能关联基础信息、支付记录、消息和统计。

本项目承载剩余模块的需求、演示原型、业务验收和研发交接。lee 负责需求及演示原型；研发同事负责生产技术方案、生产代码、真实接口联调和部署。商城继续在原项目由 lee 与 Codex 推进。

2026-11-30 是用户提出的目标版本交付节点；“完成”具体指可测版本、业务验收、试运行还是正式上线，以及当前人力是否支持该范围，仍由 Q01、Q25 确认。原建设方案截至 10 月 28 日的进度不能作为当前完成证据。

本文件维护目标、模块边界和公共业务关系。逐项范围以 [范围台账](SCOPE_REGISTER.md) 为准；待决事项见 [确认问题](OPEN_QUESTIONS.md)，来源映射见 [覆盖表](SOURCE_COVERAGE.md)，阶段及状态见 [阶段计划](STAGES.md)，执行规则见 [工作流](WORKFLOW.md)。同一事实只维护一个主位置，其他文件通过稳定编号引用。

本轮用户明确的分工和工作顺序优先，其次是本次建设方案 S0。S0 在 [覆盖表](SOURCE_COVERAGE.md) 中保留逐项映射和摘要，**不是建设方案全文归档**。有争议时应查原始消息或补充正式原文，不能将摘要当作完整原文。

商城内部沿用较新的 [P0 总体需求 S4](sources/S4_P0_REQUIREMENTS.md) 与 [六阶段计划 S3](sources/S3_P0_STAGE_PLAN.md)。[0826 总表 S1](sources/S1_0826_SCOPE_SUMMARY.md)、[0826 明细 S2](sources/S2_0826_SCOPE_DETAIL.md) 用于历史追溯；[研究需求 S5](sources/S5_RESEARCH_REQUIREMENTS_V04.md)、[研究概要 S6](sources/S6_RESEARCH_DESIGN_V04.md)、[课题立项 S7](sources/S7_RESEARCH_PROPOSAL.doc) 用于识别研究承诺和历史差异。

更新资料与旧资料冲突时，记录来源、影响编号和处理结论；未经确认的冲突进入问题台账。旧排除项不能删除本轮明确要求，旧增强项也不能自动扩大本月范围。

## 3. 产品形态与使用角色

| 终端 | 主要使用者 | 总体职责 |
|---|---|---|
| Web 管理后台 | 平台运营、社区物业管理、财务、系统管理员 | 基础档案、配置审核、业务监管、协同处理、资金查询、统计和运行管理 |
| 住户小程序 | 居民、业主及获授权成员 | 房屋车辆、缴费报修、购物预约、活动、共享互助、随手拍、积分和本人记录 |
| 商户小程序 | 商户负责人、工作人员及服务执行人员 | 准入经营、商品服务、订单履约、核销售后及本主体经营资金查询 |
| 管理端小程序 | 社区、物业、网格、维修、安全、党务及活动执行岗位 | 辖区查询、移动待办、巡查上报、工单整改复核及活动执行 |

管理端小程序由社区和物业共用，按岗位、角色及范围配置；不按每类岗位另建小程序。服务执行人员最终使用哪个入口、具备哪些身份，由所属组织和授权确认。原型的角色切换用于展示差异，不代表已完成生产登录认证。

| 商城原项目关联 | EXT-M01～08，共 8 包 | 保留商城账号、准入、商品、交易、履约、售后、资金和经营消息；本仓仅说明关联与必要演示入口 |

合计 64 个需求包是归并后的范围单位，不是菜单数量、工作量或已完成项。建设方案四端功能表 117 行及其他章节 12 项公共要求已建立映射；映射完整只说明每条有去向。社区活动暂保留在 lee 范围，Q01 确认后才能调整责任人。

成熟度与执行状态分别维护：

| 成熟度 | 后续处理 |
|---|---|
| 方向明确、待细化 | 进入相应 Stage 后补充字段、流程、权限、异常和验收 |
| 规则待确认 | 先取得业务决策；样例参数须注明为演示假设 |
| 业务范围待确认 | 取得具体场景、使用角色、现行表单和期望结果 |
| 外部条件或业务与接入待确认 | 核实厂商能力、接口、授权、样例及测试环境 |
| 有条件能力 | 无感支付、物业费积分抵扣等，确认启用条件后再实施 |
| 原项目或同事协作 | 获取责任方范围与交付证据，不能从历史计划推断完成 |

党建、网格扩展、车棚、充电、消防、城运仍保留在总范围内。待确认项不能自动删除；影响交期时，由项目负责人明确范围调整或后续安排并留痕。当前 INIT 只登记这些事项。

## 5. 核心业务对象及关系

| 对象 | 主要关系与设计边界 |
|---|---|
| 账号、人员、组织、岗位与角色 | 一个自然人可具有不同业务身份；账号、组织归属与可操作范围分别表达 |
| 社区、小区、楼栋、单元、房屋与公共点位 | 为居民关系、收费对象、服务地址和事件位置提供共同引用；网格与物业责任区域保留各自含义 |
| 居民与人房关系 | 区分人员事实、账号和业主/住户等关系；审核、有效期、解绑及家庭授权方式由 Q05 确认 |
| 车辆、停车关系与设施 | 车辆归属、停车权益、设备建档和真实接入状态分别表达，不因登记成功推定已获得权益或设备在线 |
| 经营主体、门店、人员与供给 | 服务机构关联准入、人员、服务项目及经营范围；先核验商城主体可复用部分 |
| 事件、处置任务与过程记录 | 事件保留来源，任务表达责任与处置；核实、转办、证据、复核及公开反馈可追溯 |
| 账单、预约、报名与资金事实 | 业务单据保存场景事实；支付、退款、核销和结算有各自结果与关联 |
| 积分账户、规则与流水 | 共用账户和流水，关联来源业务及有效规则，记录获得、占用、使用、释放或扣回 |

这些是产品语义，不是数据库表或接口设计。各类对象的主责系统、唯一标识及同步方向须在阶段设计和研发协作时落实。

## 6. 关键业务边界

### 6.1 统一事件与不同来源

报修、隐患随手拍、巡查及设备告警共用事件登记、责任分派、处置和复核能力，同时保留来源编号、原始证据、类别、责任主体和来源业务规则。误报、重复、撤销及转办应有处理依据。

不在总体文档中强制“一事件一工单”或“一事件多工单”；数量关系和去重方式由 Q11 确认。人员提交完成、复核通过、居民确认和评价分别表达；居民只能看到获准公开的反馈，不能看到内部敏感处置资料。

### 6.2 便民服务、活动与收费

便民服务覆盖供给审核、范围时段容量、预约、接单执行、完成及售后；活动覆盖发布、对象场次名额、报名、取消、签到与评价。服务预约与活动报名保留独立业务单据，免费业务不强制生成无意义的支付交易；收费业务关联实际收款、退款及资金结果。

改期、未到场、容量释放、取消费、自动完成及结算条件尚未冻结，分别在 Q12～Q14 确认。不得直接套用商城实物配送状态。

### 6.3 物业、停车与真实接口

物业账单的生成或导入来源、核销责任、欠费、更正和凭证口径由物业财务确认。停车金额和月卡权益以经确认的停车系统事实为依据；费用查询不等于自建计费系统。

支付成功、停车系统收到回传、权益更新或临停业务完成是不同结果。无感支付需厂商和渠道支持并取得用户授权。未接入的外部能力在原型中标为 Mock，真实接入状态另行记录。

## 7. 跨模块公共约定

DGL-011 负责形成公共约定，在相关业务实现前讨论，不能等到最终整合时补写。

- **资金：**商城、服务、物业、停车和活动分别确认收款、退款、结算及分账主体。商城已有渠道不等于其他业务可直接使用；未知、处理中和失败结果必须能区分。
- **积分：**先确认来源事实、发放时点、重复触发、退款扣回、抵扣比例上限及成本承担方。物业费抵扣是有条件能力，不先填默认比例。
- **消息：**确定触发事项、接收人、辖区范围、详情跳转及发送结果。原型消息与真实订阅/短信发送分开验收。
- **统计：**各模块先确定指标名称、时间范围、状态口径和数据来源；金额区分应收、实收、退款与结算。汇总与明细采用一致口径。
- **状态与留痕：**业务状态、资金状态、积分状态和外部同步状态分别表达；历史规则或资料变化不能无痕改变既有业务事实。

公共能力统一的是业务含义和协作关系，不预先要求研发建设特定中台、微服务或技术框架。

## 8. 权限与数据范围

角色决定可执行的动作，社区、小区、网格、组织及业务归属决定数据范围。居民查询本人和获授权业务，商户查询本主体业务；社区与物业在获准范围内协作。

居民个人资料、党务资料、视频和财务明细分别授权，查询、办理、配置及导出权限不能混用。文件和整改证据也应遵守所属业务权限。具体岗位矩阵及敏感字段见 Q03。

原型需表达角色限制、无权提示与脱敏差异；服务端鉴权、真实数据隔离和审计有效性由研发验证。原型隐藏按钮不能作为生产权限已通过的证据。

## 9. 六个 Stage 的建议边界

| 建议阶段 | 范围 | 主要依赖 |
|---|---|---|
| 00 公共基础与协作约定 | DGL-001～011 | 辖区、数据来源、身份与权限；建议提前讨论 DGL-039 基础网格关系 |
| 01 物业业务与事件闭环 | DGL-012～025；01A 收费停车、01B 工单报修隐患 | 基础关系、收款账单、责任与验收规则；两部分可分别交接 |
| 02 便民服务闭环 | DGL-026～032 | 主体复用、首批服务、预约容量及资金积分约定 |
| 03 活动与积分运营 | DGL-033～038 | 活动责任、报名签到退款及积分政策 |
| 04 网格党建与安全协同 | DGL-039～046 | 社区具体业务及设备、视频、城运条件；专项可并行确认 |
| 05 运营汇总与交付验收 | DGL-047～053 | 各模块版本、内容消息、统计口径、真实验证与上线条件 |

以上仍为建议，不把“六个 Stage”或前轮日期标为已冻结。01A/01B 是同一 Stage 内的交接分件；04 可按专项独立推进。消息、权限和统计规则随业务设计，05 负责汇总与联动。具体排期和状态统一维护在 [阶段计划](STAGES.md)。INIT 完成后按用户指示进入指定 Stage。

## 10. 复用核验与历史边界

研发需核验既有账号、商户准入、支付资金、文件消息和权限能力的适用范围，记录实际可复用、需改造和需新建部分。已有页面或相同字段名不能证明业务可直接复用。物业数据逐对象确认主责，允许档案维护、账单导入与接口查询并存。

商城保持其 LiLiShop P0 基线及原仓库，不复制商城内核；本原型仓库也不预先选定 Vue、React 或生产后端技术栈。共享互助以同事交付版本为准，统一公共身份、辖区、消息与统计边界。

旧三端调整为本次四端，活动、工单与治理安全按新方案保留。真正的开团成团、独立空间预约、社群、家庭代办、候补或多人报名、积分商城及复杂营销等进入 Q27，不因旧文档提及就自动加入本月。研究周期延续至 2027 年，模型驱动、AI 和知识图谱按课题计划另行确认；完整历史差异保留在 [覆盖表](SOURCE_COVERAGE.md)。

## 11. 后续交接与维护

进入业务 Stage 后，按 [工作流](WORKFLOW.md) 形成 REQUIREMENTS、PLAN、ACCEPTANCE、RESULT，需求编号沿用总台账。业务规则的确认必须记录问题编号、具体结论、确认人、时间及依据。

需求确认、原型通过、研发接收、生产实现和真实联调分别记录。交接使用可追溯版本、需求编号、演示入口、样例、Mock 边界、未决问题和验收证据；未取得证据不得写“全部完成”。后续变更更新受影响编号与版本，不重复建立相互冲突的范围副本。
