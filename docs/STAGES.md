## 3. 共同依赖的前置处理

1. Stage00承担整体框架与基础业务，后续Stage沿用主题、组件和应用骨架增量扩展；普通社区/小区数据可见清单不等于治理责任区域。身份、组织、主责数据、事件来源、状态、资金、积分、消息及统计约定按已审需求表达，未定政策关联问题编号，不先建设完整后台平台。
2. 积分页面可在Stage03完成，但服务发放、活动激励、商城来源、物业抵扣、退款扣回与成本承担等规则需在相关原型前确认。确认前只演示有明确标记的假设或待确认状态。
3. 支付、退款、结算和停车回传状态分别表达；各业务分别确认收款主体。原型Mock和研发真实接口联调分别验收。
4. 工单保留报修、隐患、巡查及设备告警来源，明确责任及复核；外部设备未接入不妨碍已确认的人工上报流程设计。
5. 内容、消息、权限、敏感数据与统计口径随各批细化；Stage05负责汇总与联动，不能成为所有未定义需求的默认归属。
