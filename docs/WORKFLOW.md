# 需求、演示原型与研发交接工作流

## 1. 当前起点与职责

本项目为 `daguanglu-community-prototype`，保存总体需求、分阶段需求、可操作的前端演示原型和验收交接记录。lee负责需求决策、演示评审及原型验收，Codex负责整理文档、规划原型、实施及自测；研发同事负责生产技术方案、生产代码、真实接口联调与上线交付。

INIT已完成。Stage00此前按用户确认计划形成三端小程序、Manager兼容Web及基础业务原型，并保存一次本地Git检查点，仍待lee人工验收；实际结果见其RESULT第11～12节。Stage01完整V0.3设计基线已首次导入，此前已按用户批准的联合实施计划完成01A＋01B原型，本地自测与工具限制见阶段记录，待lee统一人工验收；未决生产规则保留，Stage02～05未启动。当前任务在含最新实现的stage/01-property-parking-workorder工作区仅归整四文档及长期规则，只做文档静态检查，不重新实施或验收，不改既有证据；不安装、不启动、不构建、不执行业务测试，不切换分支、不暂存、不提交、不推送、不合并。

商城继续在原项目由Codex开发，本仓库只维护关联约定。居民共享、邻里互助按同事负责的边界协作；社区活动暂保留在lee范围，归属问题确认前不擅自转交。未取得业务确认材料时，先完成可独立推进的部分。

## 2. 项目资料与范围依据

先读 `AGENTS.md`、`README.md`、`docs/OVERALL_REQUIREMENTS.md`、`docs/STAGES.md` 和本文件。正式生成或结构修订阶段四文档前，完整读取当前本地[REQUIREMENTS模板](templates/stage/REQUIREMENTS.md)、[PLAN模板](templates/stage/PLAN.md)、[ACCEPTANCE模板](templates/stage/ACCEPTANCE.md)、[RESULT模板](templates/stage/RESULT.md)及模板目录已有说明，再读当前Stage完整四文档与实施／验收证据索引。普通局部文字修正不强迫全阶段重构。总体清单保留需求编号、来源、负责人、批次与待确认问题；建设方案的功能映射只说明有明确去向，不代表已经实现或通过验收。

以用户最新明确决定和经确认的需求为执行依据。旧文档、建设方案与新决定有差异时，记录差异、影响及处理意见；不默默删除旧需求，也不把方案中“待确认”内容改为确定规则。

## 3. 阶段与交接单位

按业务闭环跨端设计，居民、商户、管理端小程序与Web围绕同一业务事实协作。Stage 00至05为六个阶段：公共基础与协作约定、物业业务闭环、便民服务、活动与积分、网格党建与安全协同、运营汇总与交付验收。

Stage 01内的01A“收费与停车”和01B“工单、报修与隐患”是两个交接分件，共用 `docs/stages/stage-01/` 的四份文档，通过章节和任务标记区分，不再增加Stage或重复建文档。其他Stage也可按已确认需求包滚动交接。

治理、安全与城运等专项按依赖并行确认，不等前面全部完成才询问街道或厂商；启动与实施仍以获授权的范围为准。运营、消息、统计随业务补齐，最终Stage负责汇总和联动验收，不承接未定义的全部剩余需求。

## 4. 启动与需求整理

启动文档工作时在 `docs/stages/stage-XX/` 维护四文档。无论从零编写、用户附件、ChatGPT输出、Codex生成或已有版本修订，最终落盘均须遵循当前本地 `docs/templates/stage/` 对应模板。模板决定固定章节、层级、顺序、必需列及信息项，已确认需求与真实记录决定正文；完整外部输入只是内容来源，不豁免模板要求。先提取模板要求，建立简短“旧内容→模板目标章节→迁移方式／缺口”对应，可写在RESULT变更记录，不增加第五份阶段业务文档；完整迁移内容、编号和修订沿革，不以空模板覆盖，不删成摘要，不把全部旧文放入附录。

目标已有内容先核对并语义合并。Stage01首次导入的完整V0.3是历史设计基线，不要求补建本地旧版；当前以实施后最新四文档归整，禁止用早期输入包覆盖。模板“未启动／未执行”是尚无执行记录时的初始占位，不覆盖真实任务、自测、缺陷或验收结果。不适用项保留并说明依据，信息不足明确记缺口，不编造。记录实际模板路径及可取得的版本或内容摘要（如SHA-256），模板无版本号则如实注明，不增设庞大台账。文档导入与结构归整均不自动授权代码实施或业务重新批准。梳理目标、角色、对象与完整流程，再沿流程定义各端页面、字段、状态、权限、异常及跨模块关系。

已有阶段资料先与本地有效修改语义合并，不用下载包覆盖全文，也不另建`stage00`等重复目录。每个菜单按[根AGENTS第5.1节](../AGENTS.md#51-菜单功能字段规范所有stage通用)完整列出筛选、列表/卡片、表单、详情、弹窗、审核反馈、历史与结果字段，统一六列“字段名称｜字段类型／控件｜产品含义｜来源｜规则（字典／校验／联动）｜必填／可见／编辑”。保留业务编号、不列数据库内部字段，未定字典、材料及限制挂问题。PLAN说明首屏、默认列、分组／页签、办理容器及字段访问路径，ACCEPTANCE验证当前适用字段可达、条件和布局，不将全量定义理解为同屏平铺。

需求文档写清后端需要保障的业务含义，例如金额来源、重复提交、并发名额、权限判断及退款后的状态一致性。数据库、接口格式和部署架构由研发决定。先请研发判断依赖与可行性，不能以原型可点通推定生产开发可按期完成。

## 5. 问题确认与一次集中评审

每个待确认问题记录编号、具体选择、确认对象、需要的材料、建议期限、影响范围和当前临时处理。实际结论、确认人及日期未获得证据时留空。问题的建议答案或Mock值均不是冻结规则；期限是推进建议，不等于对外承诺。

Codex基于确定需求形成 `PLAN.md` 和 `ACCEPTANCE.md`。一次集中评审同时检查需求范围、关键规则、页面与交互、Mock边界、验收场景及交接分件。仅对影响范围、资金规则、外部接口或验收标准的缺口提出集中问题；独立且已明确的部分继续推进。已有授权无需逐文件、逐按钮重复确认。

集中评审前先检查四文档是否符合实际模板固定结构、必需表格列及信息项，正文是否迁入正确章节，编号／字段／页面／任务／验收及问题能否关联、总表明细与状态是否一致。检查未通过不能宣称文档已按规范交付；结构检查不代替业务确认、实施授权或lee人工验收，不能用原型当前行为反向视为需求已批准。

## 6. 原型实施与自测

仅在实施轮获得授权后按计划制作原型，实施前再次检查四文档模板结构与必需内容，核对获准范围和未决规则；不得因模板齐全推定已有实施授权。Stage00先交付三个独立小程序框架、Manager兼容Web框架及DGL-001～011；各端分别有入口、配置、身份及产物，角色切换只是演示工具。后续Stage沿用框架，报修、隐患、巡查及告警仍在对应获准阶段进入统一事件工单体系，保留来源与差异规则；支付、积分和公共身份等约定提前梳理，后续阶段沿用。

分端技术遵循[根AGENTS第6.1～6.3节](../AGENTS.md#61-分端前端技术基线2026-11-04用户确认)：Web沿用Vue 2/Manager体系，三小程序沿用uni-app/Vue 3/TypeScript/Vite，Web与移动端依赖、锁文件及构建隔离。复用前核验获准商城固定来源和发布边界；商城正式工程继续作为生产基础，新增业务经Service/Adapter只接Mock，不读商城Token、不复制生产配置、失败不回退真实接口。研发按模块接收增量，不整库覆盖。

Stage00的H5跨端事实由同源静态预览共享；微信三端分别进行本端模拟验证，预置样例切换不算跨App同步，不新增生产后端或云端Mock。网格与责任区域本次不做页面、字段、模拟对象、权限维度、地图边界、责任映射或自动分派；普通社区/小区数据可见清单不等于治理责任，DGL-039不前置。

社区、物业原型的三角色、正式产品语言、演示辅助分离、Web办理布局和微信体验统一引用[根AGENTS第5.2节及第6～6.5节](../AGENTS.md#52-社区物业原型的演示角色)，不另建一套规则。支付、退款、消息、停车、设备及城运等外部行为在文档与集中环境说明中明确Mock边界，支付确认保留不实际扣款提示；业务页面不逐字段加Mock，未接入与未知也不伪装成功。支持本阶段范围内必要的成功、失败、处理中和重试演示；消息后移的阶段不新增发送能力。真实后端、真实资金操作、真实消息发送与设备接入由研发项目承担；不得将模拟结果记为真实联调通过。

自测聚焦主流程、关键异常、跨角色状态及数据权限。获准实施后按实际项目运行必要的启动、构建和交互检查，分别记录H5、微信构建、开发者工具及具备条件的真机证据。首次导入文档轮仅做静态检查；此前实施轮按实际授权构建、启动和检查，本轮模板归整不重跑业务验证。本地Mock不能替代真实接口、工具、真机或人工验收。低影响文字或布局修正不建立无价值测试；已充分验证后停止额外回归。

实施后据真实记录回写四文档：REQUIREMENTS保留需求依据与实现偏差，PLAN区分原计划、调整及任务实际状态，ACCEPTANCE分别填写Codex自测与lee人工验收、缺陷及复测，RESULT记录实际范围、运行、限制和交接。不能长期保留已失真的“未启动／文档已导入”；也不能把历史汇总通过无依据拆成逐项通过。原始证据只读保留原版本与范围，新增或改变标准标待补验，文档静态结果不能替代业务验证。

## 7. lee验收与问题修复

提交固定的待验收版本、演示入口、角色、场景及已知问题。lee依据 `ACCEPTANCE.md` 实际操作并给出反馈，Codex据此记录通过、未通过或未执行。Codex自测通过不代替lee验收；没有真实反馈时保持“待验收”。

缺陷说明复现步骤、期望与实际结果、影响需求及修复状态。修复后复测受影响流程及必要联动，更新记录。阻塞问题与可带入交接的已知限制分别列明，由lee明确原型验收结论，不预填“全部通过”。

## 8. 固定版本交给研发

验收后在 `RESULT.md` 记录实际完成范围、需求及原型版本、证据、未完成项、Mock边界和待确认依赖。交接前再次检查四文档模板结构与必需内容、当前状态、证据及链接锚点；未通过不宣称按规范交付，文档合规也不代替lee验收或研发接收。交接包含四份文档、原型代码与启动方法、演示数据、需求映射和版本标识；Git提交或标签存在后才填写真实值，未创建时写明“未创建”。存在未提交成果时，HEAD只表示提交基线，不能冒充覆盖完整成果的固定版本；实际接收人、日期和反馈未取得时保持未交接。

研发接收后补充生产技术设计、排期与问题反馈。生产状态由研发结果和真实证据更新。前一批进入研发后，lee与Codex可继续下一批设计，不等待生产开发全部结束；有共享约定变化时同步告知受影响批次并记录影响。

## 9. 五类状态独立记录

| 维度 | 记录内容 | 不能替代的结果 |
| --- | --- | --- |
| 需求 | 未启动、整理中、待确认、已确认 | 已确认不表示原型完成 |
| 原型 | 未启动、实施中、待验收、修改中、已验收 | 已验收不表示生产可用 |
| 研发 | 未启动、开发中、提测、完成；据研发反馈填写 | 开发完成不表示接口实通 |
| 真实联调 | 未启动、受阻、进行中、通过；记录真实环境证据 | Mock或演示成功不算通过 |
| 生产验收 | 未启动、待验收、整改中、通过；据正式验收填写 | 自测、原型验收均不能代替 |

阶段进度可混合，例如已确认部分先交接，未确认部分继续挂问题。仅在适用且已说明依据时使用“不适用”，不以该状态掩盖未完成事项。

## 10. 变更、Git与日期

变更先记录原因、影响需求、来源及决定，再同步受影响的需求、计划、验收、原型和交付结果，保留已交接版本；小修正按已有授权直接完成。出现新增业务或推翻已确认规则时，整理可评审的影响后集中确认，不重开整套流程。

模板后续变化不自动推翻已验收阶段；下次获准结构修订时对齐当前模板，记录实际模板路径及可取得的版本／内容摘要，并保留历史依据。规则变更只落在本次实际修改的工作区；其他分支或worktree不会自动获得，报告需同步的公共文件，未经授权不切换、合并或推送。根AGENTS修改后显式重读；不声称其他运行会话自动加载。

普通可逆文件编辑不反复请示。Git提交、远程创建与推送按用户已给出的授权执行，授权未覆盖的新目标再确认；执行前检查工作区，保留他人修改，不强推或覆盖未知内容。建议需求确认日、原型交接日、研发承诺日和实际完成日分列；11月30日是目标版本交付节点，具体生产排期需由研发结合依赖确认。
