## 2. 目标、范围与边界

### 2.1 阶段目标

建立后续物业收费、停车、工单、服务和运营共同使用的基础信息与权限表达，并演示一条完整的人房关系流程：

基础档案准备 → 居民申请绑定 → 后台核验 → 有效关系建立 → 居民查询结果 → 关系变更或解除留痕。

不以“把所有基础配置做成一个庞大平台”为目标；基础档案和公共约定只做到后续业务能够引用、人员能够理解、原型能够验证的深度。

Stage00同时承担三个独立小程序框架＋Manager兼容Web框架＋DGL-001～011基础业务原型。整体框架复用固定、可追溯且获准的商城主题、组件、导航与工程约定；不复制商城交易全链路。后续Stage在此框架上增量扩展，正式研发按模块接收增量，不整库覆盖现有商城工程。本轮不搭建框架、不编码。

## 3. 整体业务流程与跨端协作

| 流程 | 顺序 | 完成结果 |
| --- | --- | --- |
| 基础建档 | 有权人员建社区小区 → 楼栋房屋 → 核验重复与归属 → 保存或导入 | 后续业务可引用同一房屋和空间编号 |
| 账号授权 | 建立/关联组织人员 → 关联账号 → 配置角色与数据清单 → 启用 | 不同角色看到不同菜单、数据和敏感字段 |
| 人房绑定 | 居民选择房屋及关系 → 提交申请 → Web审核 → 通过或驳回 → 住户查看结果 | 申请记录与正式关系分别保存，跨端一致 |
| 关系调整 | 提交关系变更/解除申请 → 有权人员核验 → 更新关系有效性 → 保留历史 | 不删除过去申请与本人业务记录 |
| 车辆登记 | 居民填车辆 → 校验重复/冲突 → 建档或进入核实 → 查询结果 | 建档不等于停车开通 |
| 物业资料 | 维护人员名录/文件 → 设置权限 → 获授权人员查询 | 档案与账号、文件与版本各自清楚关联 |

本稿拟采用“房屋绑定和解除由Web授权人员审核”的演示流程，待Q03、Q05确认。没有真实业务确认时，不称该流程为当地现行制度。

## 4. 角色、对象与权限

### 4.1 建议角色与权限矩阵

以下是原型角色模板，不是最终岗位名单。一个人可以有多种身份；当前使用身份与数据范围应清晰显示，不将多个身份的权限无条件相加。

| 角色模板 | 终端 | 本阶段允许的操作 | 数据及敏感信息约束 |
| --- | --- | --- | --- |
| 系统配置人员 | Web | 配置组织、账号、角色及已授权的数据清单 | 不因是系统管理员就默认能查看全部居民资料或下载全部文件 |
| 档案维护/审核人员 | Web | 维护基础档案、处理人房申请、核实冲突 | 限已授权社区/小区；查询、编辑、审核、导出分别授权 |
| 社区查询人员 | Web、管理端 | 查辖区基础概况及获准档案 | 默认脱敏；需要完整联系方式必须单独授权 |
| 物业管理人员 | Web、管理端 | 按授权维护档案、人员与文件；查询基础信息 | 不默认跨社区查看，也不默认取得党务、视频、财务权限 |
| 物业普通工作人员 | 管理端 | 查询必要位置、房屋基础资料、工作联系人 | 不展示无业务必要的住户全名单和证明材料 |
| 居民 | 住户端 | 维护本人资料、申请/查询本人房屋关系、登记本人车辆 | 同一房屋多人不自动开放彼此订单、联系方式或积分 |
| 商户/服务人员 | 商户端 | 本阶段展示本主体身份和入口边界 | 不开放居民档案；商城与服务业务按各自阶段处理 |

每项操作同时检查：当前角色允许该动作、目标对象在数据范围内、对象当前状态允许操作、敏感字段另有查看资格。页面切换社区只会缩小查询上下文，不能增加授权。

原型需要表现无权限、脱敏、按钮限制和直接进入详情的阻断；生产鉴权必须由研发在服务端验证，不能以原型隐藏按钮证明安全通过。

### 4.2 业务对象关系

| 对象 | 含义 | 关键关系/边界 |
| --- | --- | --- |
| 人员 | 自然人及必要联系信息 | 可有居民、物业员工等身份；不等于登录账号 |
| 账号 | 登录与身份关联 | 对接现有账号标识；不凭姓名或相同手机号自动合并 |
| 组织 | 社区、物业、运营、服务机构等组织 | 与人员、岗位关联；不是地理区域 |
| 社区/小区 | 空间档案层级 | 不因同名组织存在就自动授予全部数据权限 |
| 楼栋/单元/房屋 | 房屋定位及稳定引用 | 单元可以按真实结构存在或省略；不虚构单元 |
| 居民档案 | 居民业务资料 | 可先有档案、后关联账号；关联必须有核验依据 |
| 人房关系 | 某居民与某房屋的关系及有效性 | 支持一人多房、一房多人；不等于家庭代办授权或产权证明 |
| 关系申请 | 一次绑定、变更或解除请求 | 保存提交内容、审核和结果；与有效关系分开 |
| 车辆及车辆关系 | 车辆资料与居民使用关联 | 不等于停车合同、月卡、车位或通行授权 |
| 设施点位 | 设施所在位置及档案 | 不等于监测平台；维护单位不自动形成责任区域 |
| 物业人员名录 | 岗位、工作联系、在岗事实 | 可无登录账号；离岗只影响相应工作身份 |
| 文件与版本 | 一个资料主题及其历次附件 | 版本不能覆盖历史证据或扩大原有阅读权限 |

建议空间表达为：
大光路片区（当前项目固定上下文） → 社区 → 小区 → 楼栋 → 单元（可选） → 房屋。

公共设施可关联社区/小区和具体地点，不强制挂到某套房屋。初期不增加多项目SaaS配置或灵活层级编辑器。特殊地址结构取实际台账样例后处理（Q04）。

## 5. 沿流程展开详细需求

### 5.0 字段编写与前端使用口径

本章按菜单及紧密关联操作列出当前产品范围内全部用户输入、选择、展示、计算和反馈字段，覆盖筛选、列表/卡片、表单、详情、操作弹窗与历史记录。不把“姓名、电话、状态”等不同字段合并成一行；关联控件显示业务名称，不列数据库主键、外键、租户ID等技术字段。用户需要查看或搜索的业务编号仍保留，技术关联由研发在实现中处理。

字段表统一为：**字段名称｜字段类型／控件｜产品含义｜来源｜规则（字典／校验／联动）｜必填／可见／编辑**。字段类型是前端产品类型，不是VARCHAR、BIGINT等数据库类型；来源可为本人输入、档案选择、系统计算、业务动作、台账或已核验外部结果。

最后一列按“必填：…；可见：…；编辑：…”描述，区分新建、编辑、审核、已提交、已关闭等条件。系统生成字段写“自动生成，无需填写”，不能让用户手填。各菜单的页面使用表明确默认筛选与列表；详情包含其全部适用字段。状态、日期范围等筛选使用同一业务字段，不重复建立第二份事实。

字典候选、材料、格式大小限制、精度等尚未由Q02～Q06确认的内容明确标待确认；不能为“字段完整”编造256字、10MB、固定比例或法定核验材料。所有业务规则和状态流转仍以下文原流程为准。

基础网格、责任区域及其别名、地图边界、区域责任人与自动分派字段均不在本章出现为可实施字段。字段完整不等于追加身份证号、民族、学历、银行卡等本范围未要求的信息。

#### 5.3.1 绑定申请建议流程

未绑定居民 → 选择房屋 → 选择关系并填写必要资料 → 提交 → Web审核。

通过：建立/激活有效人房关系，居民能看到本人房屋关系。\
驳回：记录对外说明，居民修改后重新提交新一轮审核记录。

申请状态与关系状态分离：

| 对象 | 状态建议 | 说明 |
| --- | --- | --- |
| 关系申请 | 草稿、待审核、已通过、已驳回、已撤回 | “已通过”记录一次审核事实 |
| 人房关系 | 有效、已解除、已到期（启用有效期时） | 以后解除关系不把原审核结果改为驳回 |

| 当前状态 | 动作/角色 | 条件 | 结果 |
| --- | --- | --- | --- |
| 草稿 | 本人提交 | 房屋有效、必需信息完整 | 待审核，保存本次提交快照 |
| 待审核 | 本人撤回 | 尚无最终审核结果 | 已撤回，不产生有效关系 |
| 待审核 | 有权审核人通过 | 核验完成、数据在授权范围 | 已通过，并产生有效关系 |
| 待审核 | 有权审核人驳回 | 填写反馈原因 | 已驳回，不产生有效关系 |
| 已驳回/已撤回 | 本人修改重提 | 原问题已补充或重新选择 | 新审核轮次，旧结论保留 |
| 已通过 | 查看结果 | 本人或有权岗位 | 不能通过编辑申请直接撤销已生效关系 |

审批并发时，“撤回”和“通过”不能同时成功；第二个动作应得到当前最终结果。原型模拟该交互，真实并发原子性由研发验证。

#### 5.3.2 多人多房及冲突

支持同一居民关联多套房屋、同一房屋关联多位居民。不设置“一套房屋只允许一个居民”或“一套房屋必然只有一个业主”的固定假设。

同一居民对同一房屋不能因重复点击产生重复待审申请或重复有效关系。已有关系要变更类型时走变更核验，不追加一个权限重复的关系。发现与现有资料冲突时转人工核实，不暴露其他居民的完整资料，不自动替换他人关系。

房屋关系是平台业务核验结果，不宣称等于法定产权认证；手机号验证或微信登录也不能单独证明产权。

#### 5.3.3 变更与解除

本稿建议居民发起变更/解除申请，由Web有权人员核验；工作人员主动纠错也需原因、操作者和时间。最终是否允许居民直接解绑，由Q05确认。

解除通过后只终止相应关系及以该关系获得的新增访问资格，不删除居民账号、车辆档案、原申请、本人已发生的订单或缴费记录，也不替其他绑定人解绑。已有业务如何继续办理，在相应后续Stage设计。

解除申请被驳回时，原有效关系保持不变。重复解除只返回既有结果，不重复生成新关系。

**授权边界：**一房多人不等于家人可互查订单/积分，不自动开通代办。本人历史记录与房屋未来账单的可见性分开设计，Stage00不承诺所有绑定关系均有完整缴费权限。

**联动：**提交后Web出现相应待审；审核后住户收到模拟站内结果并能回到申请详情；通知仅包含必要内容。当前关系数量与档案关联列表同步。

**验收关联：**S00-T04、T05、T06、T07、T15。
